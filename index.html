先建立 GPU 心智模型

你可以把 GPU 看成一台擅长同时处理大量相似数字任务的机器。AI Infra 工程师需要理解的不只是芯片，还包括数据怎么到芯片、程序怎么启动、资源怎么被观测。

算力

能算多少

影响计算密集型工作。峰值算力不是应用速度保证，数据供给和并行方式也重要。

显存

能放多少

决定模型权重、激活值、缓存和并发请求能否同时驻留。

带宽与互连

数据搬多快

显存带宽、PCIe、NVLink、网络会影响数据搬运与多卡协作。

开始之前：必备概念、环境与读懂 nvidia-smi

准备周 · 后面每一章都会用到这里的词
学完后你可以：用自己的话解释 token、KV cache、prefill 与 decode、精度与量化、TFLOPS；准备好实验环境；读懂 nvidia-smi 的每一栏。

一句话：大模型就是“逐字接龙”，每接一个字都要把全部参数读一遍，所以显存放不放得下、读得多快，决定了几乎一切。

用后厨来想：客人的订单（输入）先整张读完、一起备料（prefill），然后菜一道一道地上（decode），每上一道都要把整本菜谱翻一遍；每桌的已上菜记录卡就是 KV cache，桌越多、吃得越久，备菜台越挤。

读完要能回答：

  • 为什么生成的内容越长，越占显存？
  • 为什么同一个模型量化到 4-bit 后往往更快？
  • nvidia-smi 显示 GPU-Util 100%，是不是已经满负荷？

0.0 先建立一个画面：把 GPU 想成一个后厨

这门课里的很多词第一次看会没有概念。我们先用一个贯穿全课的比喻，把它们放进同一个画面里。之后每章开头的“大白话导读”都会用这个画面来解释，看不懂正文时先回来看这张图和表。

课程里的词在后厨里是记住这一点
CPU主厨：人少但什么都会，负责下工单负责调度和准备，不做海量重复计算
GPU后厨：上千名只会简单动作的帮厨擅长把一件事拆成大量相同的小活同时做
CUDA 核心一名帮厨单个很弱，胜在人多
SM一个灶台小组，有自己的小料台活以组为单位分配
warp一排 32 名帮厨，同一时刻做同一个动作一排里动作不一致，就得分几轮做
kernel一张发给整个后厨的工单主厨递完就走，不等结果（异步）
显存（HBM）厨房里的备菜台大小决定能放多少原料
显存带宽从备菜台往灶台送料的速度逐字生成时最常卡在这里
系统内存楼下仓库大，但离得远
PCIe仓库到厨房的货梯比送料慢得多，尽量少来回搬
NVLink相邻厨房之间的传菜窗口多张卡协作时靠它
模型权重整本菜谱每做一道菜都要从头翻一遍
token一道菜（大约一个字）模型一次只出一道
prefill读完整张订单并一起备料大家同时干，拼人手（算力）
decode菜一道一道地上每道都翻一遍菜谱，拼送料速度（带宽）
KV cache每桌的已上菜记录卡桌越多、吃得越久，越占备菜台
量化把精装菜谱换成口袋本占地小、翻得快，细节可能简略
TTFT / TPOT第一道菜多久上桌 / 之后的上菜间隔客人感受到的两种“慢”
连续批处理哪桌空了立刻安排新客不让灶台闲着
OOM备菜台放不下了少接几桌、缩短记录卡或换口袋本
驱动厨房的水电燃气不通则什么都做不了
容器工具链给外包厨师开通厨房门禁没门禁，容器里看不到卡
device plugin门店向总部上报有几个灶台Kubernetes 由此知道哪里有卡
调度器 / 配额总部派单 / 每个部门的预订上限决定任务去哪、最多能用多少
MIG用墙把大厨房隔成几个小厨房互不干扰，但每间大小固定
张量并行一道菜几个厨房分工，每一步隔着窗口对料窗口慢，全体都慢
checkpoint宴席做到一半拍照存档出事后从最近的存档继续
网关前台：核对会员、限制点菜量、记账所有请求的统一入口
卡时与利用率厨房按小时租，空着也收钱每道菜的成本取决于上座率
比喻的边界：比喻只帮你建立直觉，细节以正文为准。比如真实的帮厨会思考，GPU 的计算单元不会；真实的菜谱翻一遍很快，而模型权重有几 GB 到几百 GB。

第一段 · 诞生（了解即可，国内企业基本不自己做）

①收集文字，并切成 token

发生什么从网页、书籍、代码里收集海量文字。用“分词器”把文字切成 token，每个 token 对应一个编号。分词器的规则会和模型一起发布，用的时候必须配套。用到的概念token、分词器后厨里采购原料，并按统一规格切好、编号。对应章节0.1

②预训练：做几万亿道“猜下一个字”

发生什么参数先随机填，然后反复做“读前面的字、猜下一个字”。猜错了就算出每个参数该往哪个方向调（梯度），调一点点，再做下一道。最后得到几十亿个调好的参数。用到的概念参数、梯度、训练显存（每个参数约 16 字节）、多卡并行、all-reduce、checkpoint、成组调度卡在哪里成百上千张 GPU 连续算几周到几个月；卡间通信和存储吞吐常常是瓶颈。后厨里用无数次试菜，慢慢写出一本厚厚的菜谱。对应章节0.1 的注释、第 4、11 章

③对齐：从“会接话”到“会聊天”

发生什么用人工写好的问答继续训练（指令微调），再根据人对回答好坏的评价做调整。企业要适应自己的业务时，在这一步之后再做少量微调，常用 LoRA。用到的概念微调、LoRA后厨里菜谱写好后，再按客人口味做最后的调整。对应章节第 11 章 11.4

④发布权重文件

发生什么把参数存成文件发布出来，通常包括：权重文件（safetensors）、结构说明（config.json，写着层数、注意力头数等）、分词器。社区还会做出量化版本（AWQ、GPTQ、GGUF）。用到的概念权重、层、量化、精度（BF16、INT4）后厨里菜谱印刷出版：有精装本，也有口袋本。对应章节0.3、第 4 章、第 13 章

第二段 · 部署（AI Infra 工程师的主要工作从这里开始）

⑤下载权重，放进内部存储

发生什么从 ModelScope 等国内模型库下载，校验文件完整，存到内部对象存储或节点本地盘。生产环境只从内部拉取。用到的概念模型仓库、离线交付卡在哪里网络和存储：几十 GB 的文件，下载和分发都慢。后厨里把菜谱从书店买回来，放进自己的仓库。对应章节第 10 章 10.3、第 13 章 13.3

⑥启动推理引擎：把权重搬进显存，预留 KV cache

发生什么引擎把权重从磁盘读进内存，再经过 PCIe 拷进显存。然后按设定的比例（如 90%）把剩下的显存预先划给 KV cache。这就是 vLLM 一启动就“占满”显存的原因。用到的概念显存、PCIe、KV cache、OOM、冷启动、就绪探针卡在哪里磁盘和 PCIe 的速度决定启动要几分钟；显存放不下权重就直接 OOM。后厨里把菜谱搬上备菜台，再给每桌的记录卡留出地方。对应章节第 4、9、10 章

第三段 · 回答一次提问（以“什么是显存？”为例）

⑦请求到达网关

发生什么网关检查 API 密钥，按 token 数限流，记下是谁调用了哪个模型，再把请求转给某个推理副本。用到的概念网关、鉴权、限流、路由、多副本卡在哪里一般很快；网关配置不当时会成为单点。后厨里前台核对会员卡、限制点菜量、安排去哪家分店。对应章节第 10 章 10.2

⑧在引擎里排队

发生什么引擎的调度器决定这个请求什么时候开始算。如果 KV cache 还有空间，它会被立刻加入正在运行的那一批（连续批处理）；没空间就排队等。用到的概念排队、连续批处理、并发、KV cache 使用率卡在哪里KV cache 满了就要等，这段等待会直接算进 TTFT。后厨里有空桌就马上入座，没空桌就在门口等位。对应章节第 5、9 章

⑨分词：文字变成 token 编号

发生什么“什么是显存？”被切成几个 token，变成一串编号。这一步在 CPU 上做。用到的概念token、分词器卡在哪里通常很快；CPU 被占满时会拖慢。后厨里把客人的订单翻译成厨房内部的菜品编号。

⑩编号变成向量

发生什么每个编号去一张大表里查出一串数字（向量），作为它进入第 1 层前的“初始理解”。这张表本身也是参数的一部分。用到的概念参数、向量后厨里按菜品编号取出对应的基础配方卡。

⑪Prefill：把整个问题一次读完

发生什么问题里的所有 token 一起依次穿过每一层（7B 模型约 28 层）。每一层先做注意力（每个字和前面的字对照），再做一次计算加工；同时把每个字在这一层的 Key 和 Value 存进 KV cache。走完最后一层，得到第一个要输出的字的候选。用到的概念层、注意力、KV cache、矩阵乘、kernel、SM、Tensor Core、张量并行（多卡时）卡在哪里很多字同时算，运算量大，主要受算力限制。问题越长，这一步越久。多卡张量并行时，每一层都要经 NVLink 通信一次。后厨里整张订单一起读完、一起备料，拼的是人手。对应章节0.2、第 3、5、9 章关键指标从请求到达到这一步结束（含 ⑦ ⑧ ⑨），就是 TTFT。

⑫从候选里选出一个字

发生什么最后一层算出“每个可能的字有多大概率是下一个”，再按设定的规则选一个。温度越低，越倾向选概率最高的；温度越高，回答越多样。用到的概念概率、采样、温度后厨里从几道候选菜里挑出要上的那一道。

⑬Decode：一个字一个字地生成 ↻

发生什么把刚选出的字当作新输入，只算这一个字：它再依次穿过每一层，每层从 KV cache 里读出前面所有字的笔记，不用重算；同时把自己的笔记追加进去。然后回到 ⑫ 选下一个字。重复，直到生成结束符或达到长度上限。用到的概念decode、KV cache、显存带宽、批处理、量化、TPOT卡在哪里每生成一个字，都要把全部权重从显存读一遍，而运算很少，所以主要受显存带宽限制。同一批里的多个请求可以共用这次读取，这就是批处理能大幅提高吞吐的原因。KV cache 每步变大一格，满了就要排队甚至 OOM。后厨里菜一道一道地上，每道都要把整本菜谱翻一遍；同时招待多桌，翻一遍能顺便给几桌出菜。对应章节0.2、第 1、4、9 章关键指标相邻两个字的间隔，就是 TPOT。

⑭流式返回：一边生成一边发

发生什么每生成一个 token，就转回文字，通过网关推送给用户（流式输出），所以你看到回答是一个字一个字冒出来的。用到的概念流式输出、反分词后厨里做好一道上一道，不等整桌做完。

⑮结束：释放空间，记账

发生什么这个请求的 KV cache 被释放，空出的位置马上给排队中的请求用。网关记下这次用了多少输入和输出 token。用到的概念KV cache、token 用量、每百万 token 成本后厨里客人离席、收拾桌子、记账。对应章节第 10、13 章

0.1 大模型在做什么

大语言模型做的事情是根据已有的文字，预测下一个 token。token 是文字被切成的小片段，一个汉字大约对应 1 到 2 个 token。模型每次只生成一个 token，再把它接到输入后面继续预测，这叫自回归生成。

  • 参数（权重）：模型里学到的数字。“7B 模型”指有约 70 亿个参数，它们要全部放进显存。
    注释：“参数”到底是什么？为什么要全部放进显存？（点开看）

    先看一个最小的例子。假设用面积估算房价，写了一个公式：房价 = a × 面积 + b。a 和 b 一开始不知道是多少，拿一堆真实成交数据去试，不断调整，直到算出来的房价和真实价格最接近，比如最后得到 a = 3.2、b = 15。

    • a 和 b 就是“参数”，也叫“权重”。
    • “学到的”指它们不是人手写的，而是用数据反复调出来的，这个过程就是训练。
    • 这个公式只有 2 个参数。

    大模型是同一回事，只是大得多。大模型也是一个公式：输入前面的文字，输出下一个字。只是它的系数不是 2 个，而是几十亿个。“7B”里的 B 是 billion（十亿），7B 就是大约 70 亿个这样的数字。模型“懂”多少东西，全靠这 70 亿个数字被调成了合适的值。下载一个模型，下载的主要就是这些数字，所以 7B 模型的文件有十几 GB。

    为什么要全部放进显存：

    1. 每生成一个字，70 亿个参数都要用一遍。公式要从头算到尾，每个系数都参与计算。
    2. 数字放得越近，算得越快。GPU 只能高效使用自己显存里的数据；放在硬盘或内存里，每生成一个字都要搬一遍十几 GB，慢到没法用。
    3. 算一下要多大地方。每个参数用 BF16 格式存要 2 个字节：70 亿 × 2 字节 ≈ 14 GB。所以 7B 模型光参数就要占约 14 GB 显存，16 GB 的卡装下它就几乎满了。

    用后厨比喻：参数就是那本“菜谱”。菜谱越厚（参数越多），模型越聪明，但备菜台（显存）要越大才放得下。每上一道菜（每生成一个字）都要把整本菜谱从头翻一遍，所以菜谱必须摆在手边，不能放在楼下仓库。

    注释：这些参数是怎么来的？（点开看）

    一句话：参数是“训练”出来的。先随便给一组数，再用海量文字反复试，猜错了就把每个参数往“少错一点”的方向微调一下，重复几万亿次。

    还是用房价公式来看。公式是“房价 = a × 面积 + b”，训练过程是：

    1. 先随便猜。a 和 b 先填两个随机数，比如 a = 1、b = 0。
    2. 拿一条真实数据试。一套 100 平米的房子，公式算出 100 万，实际成交 335 万。
    3. 算差多少。少算了 235 万，这个差距叫“误差”。
    4. 往减小误差的方向调一点点。算少了，就把 a、b 都调大一点。每次只调一点点，调太猛会来回冲过头。
    5. 换下一条数据，重复。几千条数据反复过很多遍，a 和 b 就慢慢稳定在最合适的值上。

    第 4 步“往哪个方向调、调多少”，有一个数学方法能直接算出来，叫梯度。整个“算误差、按梯度微调”的过程叫梯度下降。

    大模型是同一个过程，只是规模大得多：

    • 题目：不是猜房价，而是“读前面的字，猜下一个字”。比如给它“床前明月”，让它猜下一个字。
    • 数据：从网页、书、代码里收集的海量文字。每段文字都能自动变成无数道“猜下一个字”的题，不需要人工出题。比如 Qwen2.5 的技术报告说预训练用了约 18 万亿个 token。
    • 过程：猜错了就按梯度把 70 亿个参数各自微调一点点，再做下一道题。几万亿道题做下来，参数就被调成了“很会接话”的状态。语法、常识、推理能力，都是在反复猜下一个字的过程中逼出来的。
    • 代价：要用成百上千张 GPU 连续算几周到几个月。

    预训练之后，还有一步让它“会聊天”。预训练出来的模型只会接话，还不会好好回答问题。接下来要用人工写好的“问题和标准回答”继续训练（指令微调），再根据人对回答好坏的评价做调整，最后才得到能对话的模型。这一步的数据量小得多。

    和 AI Infra 工作的关系：

    1. 为什么训练比推理费显存。训练时除了参数本身，还要存每个参数的梯度，以及优化器为每个参数记的“调整历史”。这就是第 4 章说的“训练大约每个参数 16 字节”，而推理只要 2 字节。
    2. 国内企业基本不从头训练。通常直接下载别人训练好的参数（Qwen、DeepSeek 等开源模型），这就是“下载模型”；需要适应自己的业务时，再用少量数据做微调，比如 LoRA 只调整一小部分新增参数。所以工作重点是部署推理服务和支撑微调任务。
  • 层：模型由几十个结构相同的层叠起来，输入要依次经过每一层。
    注释：“层”是什么？为什么要一层一层地过？（点开看）

    一句话：一层就是一道加工工序。输入的文字先变成一串数字，然后像流水线上的零件一样，依次经过几十道工序，每经过一道，模型对这段话的理解就更深一点，最后一道给出“下一个字是什么”的猜测。

    用“一份文稿经过 28 位编辑”来想：

    • 一句话交给第 1 位编辑，他在每个字旁边写上自己的理解，再把稿子传给第 2 位；第 2 位在第 1 位的基础上再加工，再传下去……直到第 28 位。
    • “结构相同”：28 位编辑的工作流程一模一样：先把每个字和前面所有字对照一遍（这一步就是“注意力”），再单独细想每个字。但每位编辑手里的“经验”不一样，这些经验就是各层自己的参数。
    • 分工大致是：前面几层更多地处理字词和语法，中间几层处理含义和上下文，最后几层为猜下一个字做准备。这是研究者观察到的大致倾向，不是人为规定的。
    • “依次经过”：第 2 位必须等第 1 位改完才能开工，不能跳过谁。

    用数字看一下：Qwen2.5-7B 有 28 层。它的约 76 亿个参数，大部分平均分布在这 28 层里，每层大约 2 亿多个（估算值）；剩下的在“把字变成数字”和“把数字变回字”的开头和结尾部分。层数越多、每层越宽，参数就越多。

    后厨里：一道菜要依次经过 28 个工位加工，每个工位的布局一样，但各有各的菜谱页。上一道菜，就是把 28 个工位走一遍、把 28 页菜谱都翻一遍。

    和 AI Infra 工作的关系：

    1. 每生成一个字，都要从第 1 层走到最后一层。所以每个字都要把全部参数读一遍，这就是 decode 受显存带宽限制的原因。
    2. KV cache 公式里有“层数”。每一层都要为每个字单独留一份笔记（Key 和 Value），就像 28 位编辑各自保留自己的批注，所以层数越多，KV cache 越大。
    3. 流水并行就是按层切。一张卡放不下时，可以把第 1 到 14 层放在卡 A、第 15 到 28 层放在卡 B，数据从 A 算完再传给 B。第 9 章里的 PP 讲的就是这个。
  • 上下文长度：一次能看到的 token 上限，包括输入和已经生成的输出。
  • 推理与训练：推理是用现成的权重生成结果；训练是反复调整权重，要额外保存梯度和优化器状态，所以更吃显存。微调是在已有模型上用少量数据继续训练，LoRA 是只训练一小部分新增参数的省钱做法。

0.2 注意力、KV cache、prefill 与 decode

每一层里最关键的运算叫注意力：处理当前 token 时，回头看前面所有 token。为此，每个 token 在每一层都会算出一对向量，叫 Key 和 Value。注意力分成若干个“头”并行计算，每个头的向量长度叫 head_dim。

前面 token 的 Key 和 Value 不会变，所以算过一次就存起来，这就是 KV cache。它让生成新 token 时不必重算历史，代价是占显存，而且随 token 数和并发请求数线性增长。

0.3 精度与量化

每个参数用多少位来存，叫精度。位数越少，占显存越小、搬运越快，但可能损失效果。把高精度权重转换成低精度，叫量化。

格式每个参数7B 模型的权重大小常见用途
FP324 字节约 28 GB早期训练，优化器内部的主权重
FP16 / BF162 字节约 14 GB当前训练和推理的默认精度；BF16 数值更稳定
FP81 字节约 7 GB新一代 GPU 支持的训练与推理精度
INT81 字节约 7 GB推理量化
INT4 / 4-bit0.5 字节约 3.5 GB小显存设备上的推理，效果下降更明显

TF32 是 A100 起引入的一种内部计算方式，用于加速 FP32 运算，了解即可。量化模型常见的文件和方法名有 AWQ、GPTQ（配合 vLLM 等引擎）和 GGUF（配合 llama.cpp、Ollama）；不做量化的原始权重通常是 safetensors 格式。

0.4 两个最常用的硬件单位

  • FLOPS：每秒浮点运算次数。1 TFLOPS 是每秒一万亿次，1 PFLOPS 是 1,000 TFLOPS。它衡量“算得多快”。
  • 稠密与稀疏口径：厂商宣传的算力常按“稀疏”计算，是普通（稠密）数值的 2 倍。比较时要统一口径，本课程一律用稠密。
  • 显存带宽（GB/s、TB/s）：每秒能从显存读写多少数据。它衡量“搬得多快”。
  • 怎么判断哪个是瓶颈：运算多而数据少的任务（矩阵乘、prefill、训练）受算力限制；每读一个数只做一两次运算的任务（decode）受带宽限制。

先看示范用三步法解释“显存带宽”

解释一个概念时，按三句话来：它是什么、为什么需要它、没有它会怎样。

  1. 它是什么：每秒能从显存里读写多少数据，比如 T4 约 320 GB/s。
  2. 为什么需要它：模型每生成一个字，都要把全部权重从显存读一遍。7B 模型用 INT8 存约 7 GB，读一遍就是 7 GB 的数据量。
  3. 没有它会怎样：320 GB/s 读 7 GB 至少要约 22 毫秒，所以单个请求每秒最多生成约 45 个字。带宽越低，字出得越慢，和算力多强关系不大。

合格的解释有两个标准：外行能听懂；至少带一个数字或例子。

轮到你：按这几步做
  1. 照三步法写“KV cache 为什么占显存”。检查点：第三句里出现了“并发”或“上下文长度”。
  2. 写“prefill 和 decode 的瓶颈为什么不同”。检查点：两句话里分别出现“算力”和“带宽”。
  3. 算 BF16 和 INT4 的 7B 模型权重各多大。检查点：答案约 14 GB 和 3.5 GB；算错就回看 0.3 的表。
  4. 写稠密和稀疏算力口径的关系。检查点：能说出“差 2 倍，比较时要统一”。
  5. 写 GPU-Util 100% 是否说明满负荷。检查点：能说出它只表示“有没有在算”，不表示“算了多少”。

练习参考答案
KV cache 保存每个历史 token 在每一层的 Key 和 Value，随 token 数和并发线性增长。Prefill 并行处理全部输入，运算密集，受算力限制；decode 每步都要读全部权重而运算很少，受显存带宽限制。BF16 约 14 GB，INT4 约 3.5 GB。稀疏口径是稠密的 2 倍。不能，GPU-Util 只表示采样时间内有计算在运行，算力和带宽都可能还有余量。
自测：一个 7B 模型说自己“支持 32K 上下文”，为什么不等于你的 24 GB 显卡能跑 32K？
权重按 BF16 约占 14 GB，剩下的显存要放 KV cache。KV cache 随上下文长度和并发数增长，32K 上下文加上几路并发就可能超出剩余显存。能跑多长的上下文要按第 4 章的公式算。
自测：nvidia-smi 显示 CUDA Version 12.4，是否说明系统里装了 CUDA 12.4？
不是。它表示当前驱动最高支持到 CUDA 12.4。实际使用的 CUDA 运行库通常随框架或容器镜像一起提供。
自测：为什么同一个模型，量化到 4-bit 后往往生成更快？
权重变小后，decode 每一步要从显存读取的数据量减少，而这个阶段正好受显存带宽限制，所以速度提升。代价是效果可能下降，需要用业务评测集确认。

1.1 GPU 为什么适合 AI

CPU 通常有少量复杂核心，擅长分支、操作系统和流程控制；GPU 有大量并行执行资源，适合把同一类数值运算应用到大量数据上。神经网络里的矩阵乘法、向量运算和张量变换，常能拆成许多并行工作。

这不是“GPU 永远比 CPU 快”。数据规模太小、频繁在 CPU/GPU 之间搬运数据、任务含大量串行控制时，GPU 可能无法发挥优势。作为 SRE，你要问的是：瓶颈在计算、内存、互连、排队还是软件栈？

1.2 GPU 节点的关键组成

  • GPU 芯片：包含执行计算的多个 SM（Streaming Multiprocessor）等单元。不同代际的 SM 资源、指令能力和数量不同。
  • 显存（通常为 HBM/GDDR）：GPU 本地内存。AI 工作集通常需要驻留在这里，容量不足会导致分配失败、降批次或性能显著下降。
  • CPU 与系统内存：负责启动 GPU 工作、准备数据、服务请求、运行操作系统和容器。
  • PCIe / NVLink：CPU 到 GPU 或 GPU 之间的数据通路。多 GPU 训练和推理还依赖通信拓扑。
  • 供电、散热与主板：功耗限制、温度和链路错误会影响稳定性与持续性能。
指标回答的问题常见误读

    补上硬件到性能的桥梁GPU 内部存储层次与 Tensor Core

    前面说“显存带宽”，这里再往芯片里面走一层。数据离计算单元越近，通常延迟越低、容量越小；离计算单元越远，容量更大，但搬运成本更高。性能优化经常是在这些层之间减少重复搬运。

    • 寄存器：线程私有，速度快但有限；寄存器需求高可能减少同一 SM 上可同时驻留的 warp。
    • Shared Memory：程序可显式使用的 SM 内共享存储，适合线程块内复用数据；访问模式不佳可能发生 bank conflict。
    • L1/L2 Cache：缓存降低重复访问显存的成本；缓存命中率和数据访问模式会影响真实带宽。
    • HBM：容量大、带宽高于主机内存，但仍远慢于片上存储；大模型权重和 KV cache 的容量/带宽约束通常落在这里。
    • Tensor Core：执行矩阵乘累加的专用硬件。它不是“自动让所有模型更快”的开关；框架、数据类型、矩阵形状和算子实现都要匹配。

    工程含义：同一个 GPU 上，如果一个算子不断从 HBM 读写临时张量，可能比把数据暂存在片上并复用更慢；如果模型算子没有使用支持的矩阵计算路径，标称 Tensor Core 峰值也用不上。

    延伸阅读：CUDA Programming Guide：内存层次 · CUDA Best Practices：数据访问与占用率

    自测：为什么把数据从 HBM 搬到 Shared Memory 并复用，可能提升性能？
    参考思路：如果多个线程/计算步骤重复使用同一数据，片上存储可避免重复访问较慢的 HBM；但搬运和同步也有成本，必须确认数据确实被复用并测量。

    参数T4 的数值它限制什么

    显存带宽约 320 GB/s决定出字速度的上限。INT8 的 7B 权重约 7 GB，读一遍约 22 毫秒，单请求最多约 45 字/秒；4-bit 约 3.5 GB，上限约 90 字/秒。实际会更低。

    软件栈：GPU 如何从主机进入程序

    第 2 周 · 理解驱动、CUDA、框架、容器和设备发现
    学完后你可以：说清驱动由哪几部分组成；分清四种“CUDA 版本”和计算能力，判断一个镜像能不能在某台机器上跑；解释容器是怎么拿到 GPU 的；读懂 9 类常见报错并知道在哪一层修。

    一句话：程序要用上 GPU，得经过“硬件、驱动、容器、框架”一层层打通，哪一层断了，就在哪一层看不到卡。

    用后厨来想：厨房设备在（硬件），水电燃气通了（驱动），外包厨师有门禁卡（容器工具链），厨师会用这套灶具（框架带 CUDA）。排查就是从下往上一层层确认。

    读完要能回答：

    • 主机上能看到卡、容器里看不到，问题最可能在哪一层？
    • 驱动和 CUDA 版本是什么关系？
    • 为什么容器镜像里不需要装驱动？
    • 报错“no kernel image is available for execution on the device”说明什么？

    2.1 分层排查法

    1. 硬件与主机：系统是否枚举到 GPU？内核模块和设备节点是否正常？
    2. 驱动接口：主机上的驱动能否与管理工具通信？驱动版本是否适配目标设备与运行时？
    3. 容器设备暴露：容器是否获得 GPU 设备节点和所需驱动库？容器运行时是否正确配置？
    4. 框架与 CUDA：框架构建是否包含对应 CUDA 支持？运行时库是否能加载？
    5. 应用与权限：环境变量、设备权限、cgroup、进程占用或安全策略是否阻止访问？

    像排查网络一样，逐层验证“设备存在—设备可访问—运行时可初始化—框架可执行一个小算子”，不要一次性重装所有组件。

    # 在 GPU 主机查看设备与驱动概况 nvidia-smi # 在容器里验证设备透传（需使用已配置 GPU 的容器运行时） nvidia-smi # Python / PyTorch 验证框架是否发现设备 python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.device_count())"
    版本判断：“CUDA 版本”可能指驱动支持的 CUDA 兼容级别、Toolkit 版本或框架构建版本，排障时先确认具体指哪一个。生产变更前以厂商兼容矩阵和组织验证结果为准。

    2.2 驱动到底装了什么

    “装驱动”其实装了好几样东西，分散在内核和用户空间。排障时要知道每一样在哪、怎么查。

    组件作用怎么查
    内核模块：nvidia、nvidia_uvm、nvidia_modeset、nvidia_drm直接控制硬件。nvidia_uvm 负责统一内存，CUDA 程序需要它。lsmod | grep nvidia
    设备文件：/dev/nvidia0、/dev/nvidiactl、/dev/nvidia-uvm 等程序通过这些文件和驱动通信。容器要用 GPU，本质上就是把它们放进容器。ls -l /dev/nvidia*
    用户态库：libcuda.so（CUDA 驱动接口）、libnvidia-ml.so（NVML 管理接口）程序和 nvidia-smi 都通过它们调用驱动。版本必须和内核模块完全一致。ldconfig -p | grep -E "libcuda|libnvidia-ml"
    nvidia-smi基于 NVML 的管理和查看工具。nvidia-smi -q | head -20
    nvidia-persistenced让驱动常驻内存，避免每次调用都重新初始化。systemctl status nvidia-persistenced
    nvidia-fabricmanager（只有带 NVSwitch 的多卡机型需要，如 HGX 8 卡）管理卡之间的 NVSwitch 互连。没启动时 nvidia-smi 一切正常，但 CUDA 程序初始化失败（报错 802）。版本必须和驱动一致。systemctl status nvidia-fabricmanager
    记住一点：驱动版本同时存在于两个地方：内核模块和用户态库。升级驱动后如果没重启，内核里还是旧模块、磁盘上已是新库，两边对不上，就会报“Driver/library version mismatch”。

    2.3 版本兼容：四种“CUDA 版本”和三条规则

    平时说“CUDA 版本”，可能指四样不同的东西。排障时第一步是弄清楚说的是哪一个。

    指的是在哪看由谁决定
    驱动支持的最高 CUDA 版本nvidia-smi 右上角的 CUDA Version主机驱动的版本
    CUDA Toolkit 版本（nvcc 编译器）nvcc --version你装的开发工具。只有要编译 CUDA 代码时（如编译某些推理加速扩展）才需要，跑模型不需要
    框架自带的 CUDA 运行库版本python -c "import torch; print(torch.version.cuda)"你装的 PyTorch 包，文件名里的 cu121、cu124 就是它
    容器镜像要求的 CUDA 版本镜像标签，如 cuda:12.4.1；或镜像里的 NVIDIA_REQUIRE_CUDA 环境变量镜像的制作者

    三条兼容规则：

    1. 新驱动能跑旧 CUDA。只要“驱动支持的最高版本”不低于程序需要的版本，就能跑。nvidia-smi 显示 12.4、torch 显示 12.1，没问题；反过来就不行。
    2. 同一大版本内有小版本兼容。用较新的 12.x 编译的程序，通常也能在只支持较早 12.x 的驱动上运行，但个别新功能不可用。
    3. 数据中心 GPU 有“前向兼容包”。安装 cuda-compat 后，可以在旧驱动上跑更新的 CUDA，但有适用范围和限制，用之前看 NVIDIA 的兼容性文档。

    由此得出两个生产上的结论：PyTorch 的 pip 包自带 CUDA 运行库，所以服务器上不装 CUDA Toolkit 也能跑模型，只要驱动够新；生产上倾向于升级驱动，因为新驱动兼容旧程序，升一次所有业务镜像都受益，而降级框架要逐个改镜像。

    第五个容易忽略的版本：计算能力（compute capability）。每一代 GPU 有一个架构编号。框架和推理引擎编译时，要包含你这张卡的编号，否则会报“no kernel image is available for execution on the device”。

    计算能力常见型号
    7.0V100
    7.5T4
    8.0A100、A30
    8.6A10、RTX 3090
    8.9L4、L40S、RTX 4090
    9.0H100、H200、H20
    10.0B200

    一个和你直接相关的例子：一些常用的推理加速库只支持较新的架构，比如 FlashAttention 2 要求 8.0 及以上。在 T4、V100 上，推理引擎会自动换成较慢的实现，或者某些功能直接不可用。所以同一个模型，在 T4 上测出来的性能不能直接推到 A10 或 A100 上。

    判断一个镜像能不能在这台机器上跑，查三件事：

    # 1. 驱动支持到哪个 CUDA、这张卡的计算能力是多少 nvidia-smi --query-gpu=name,driver_version,compute_cap --format=csv nvidia-smi | head -4 # 2. 框架用的 CUDA 版本、编译时包含了哪些架构 python -c "import torch; print(torch.__version__, torch.version.cuda); print(torch.cuda.get_arch_list()); print(torch.cuda.get_device_capability(0))" # 3. 带 NVSwitch 的多卡机型：fabric manager 是否在运行 systemctl is-active nvidia-fabricmanager

    判断标准：驱动支持的 CUDA ≥ 框架的 CUDA；卡的计算能力（如 7.5 对应 sm_75）在框架的架构列表里；多卡机型的 fabric manager 是 active。

    2.4 容器是怎么拿到 GPU 的

    1. 你用 docker run --gpus all，或在 Kubernetes 里申请 nvidia.com/gpu。
    2. 容器运行时被配置成 NVIDIA 的运行时（nvidia-container-runtime，它在标准的 runc 外面包了一层）。
    3. 创建容器之前，工具链（libnvidia-container）把三样东西放进容器：设备文件（/dev/nvidia*）、主机上的驱动用户态库（libcuda.so、libnvidia-ml.so 等）、nvidia-smi 等工具。
    4. 容器里的程序像在主机上一样调用 GPU。

    这就是“镜像里不用装驱动”的原因：驱动库是从主机挂进来的，天然和主机的内核模块版本一致。反过来，如果镜像里自己打包了一份 libcuda.so，反而可能和主机驱动冲突，出现版本不一致的报错。用后厨来说：门禁卡让外包厨师进门，工具链还要把厨房的水电接口接到他的工位上。

    两个最容易混的环境变量：

    变量谁读它、什么时候读作用
    NVIDIA_VISIBLE_DEVICES容器工具链，在创建容器时决定把哪几张卡放进容器。Kubernetes 的 device plugin 分配卡时，就是通过它（或 CDI）告诉工具链
    CUDA_VISIBLE_DEVICES容器里的 CUDA 程序，在进程启动时在已经看得到的卡里再挑几张，并重新从 0 编号

    例子：容器拿到了主机的 2、3 号卡，在容器里它们叫 0、1；如果再设 CUDA_VISIBLE_DEVICES=1，程序只看到原来的 3 号卡，名字叫 cuda:0。日志里的卡号和主机上的卡号对不上时，用 UUID（nvidia-smi -L）来对。

    一个安全隐患：如果节点把 NVIDIA 运行时设成了默认运行时，一个没有申请 GPU 的 Pod，只要自己写上 NVIDIA_VISIBLE_DEVICES=all，就可能绕过调度、拿到这台机器上的所有卡。生产上要通过工具链和 device plugin 的配置堵住它，例如改用挂载卷或 CDI 的方式传递设备列表，并禁止非特权容器用环境变量申请设备。具体参数名以所用版本的文档为准。

    新的标准方式：CDI（容器设备接口）。工具链先生成一份设备描述文件，容器运行时按这份文件注入设备，不再依赖环境变量和定制的运行时。Docker、Podman、containerd 和新版本的 GPU Operator 都在往这个方向迁移。

    sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml # 生成设备描述文件 nvidia-ctk cdi list # 列出可用设备名，如 nvidia.com/gpu=0 docker run --rm --device nvidia.com/gpu=all ubuntu nvidia-smi -L # 需要较新的 Docker 并开启 CDI 支持

    Kubernetes 节点上，容器运行时一般是 containerd。用 nvidia-ctk runtime configure --runtime=containerd 写好配置并重启 containerd；GPU Operator 还会创建一个名为 nvidia 的 RuntimeClass，Pod 可以显式指定用它。

    2.5 驱动的安装与升级：生产上怎么做

    • 三种安装方式：①用发行版或 NVIDIA 官方软件源的包（推荐，通常带 DKMS，内核升级时会自动重新编译模块）；②官方 .run 安装包（灵活，但难以统一管理）；③用 GPU Operator 以容器的方式装驱动（节点上不直接装，升级由 Operator 统一做）。云厂商的 GPU 镜像通常已预装驱动，做实验时最省事。
    • 选版本：用 NVIDIA 的长期支持生产分支，整个集群统一一个版本，写进版本矩阵。
    • 锁内核：系统自动升级内核，是“重启后 GPU 不见了”最常见的原因。要么锁定内核包，要么确认 DKMS 能为新内核编译成功。
    • 两个常见拦路虎：开源的 nouveau 驱动必须禁用，否则会抢占显卡；开启了安全启动（Secure Boot）的机器，未签名的内核模块加载不了。
    • 新一代 GPU：NVIDIA 推荐、部分新架构要求使用开源内核模块版本（nvidia-open），安装前看该驱动版本的说明。
    • 国内环境：NVIDIA 官方软件源在国内可能很慢，可以用云厂商预装驱动的镜像、内部的 apt/yum 代理，或提前下载好离线安装包。
    • 升级流程：按第 7 章“GPU 节点基线”里的滚动升级步骤做，不要在有业务的节点上直接升级。
    cat /proc/driver/nvidia/version # 当前加载的内核模块版本 modinfo nvidia | grep ^version # 磁盘上模块文件的版本，和上一行对不上说明需要重启 dkms status # 用 DKMS 安装时，看是否为当前内核编译过 uname -r # 当前内核版本 mokutil --sb-state # 是否开启了 Secure Boot lsmod | grep nouveau # 应该没有输出

    并行执行：线程、warp 与 kernel

    第 3 周 · 不写复杂 CUDA，也要理解执行模型
    学完后你可以：读懂 GPU 计算任务的基本组织方式，并理解并行度、分支和资源占用对性能的影响。

    一句话：GPU 把一个大任务拆成成千上万个一模一样的小任务，同时交给大量简单的计算单元去做。

    用后厨来想：主厨下一张工单“把 1000 个土豆切丁”（kernel）；每个帮厨负责一个土豆（thread）；工单分成若干批（block）派给各灶台小组（SM）；组里每 32 个帮厨排成一排、同一时刻做同一个动作（warp）。如果一排里有人切丁、有人切片（分支），这一排就得分两轮做，变慢。

    读完要能回答：

    • thread、block、warp 分别是什么？
    • 为什么 kernel 里要写边界判断？
    • 为什么代码里的分支会让 GPU 变慢？

    3.1 从一个向量加法开始

    假设两个长度为 N 的数组逐元素相加，CPU 可以循环处理；GPU 可以把多个元素分配给大量线程。每个线程计算自己的索引，读取两个数、相加并写回。程序中在 GPU 上执行的函数通常称为 kernel。

    # 概念伪代码：每个线程处理一个元素 index = block_id * threads_per_block + thread_id if index < N: C[index] = A[index] + B[index]

    3.2 重要术语

    • Thread：逻辑上的单个执行线程，有自己的索引和局部状态。
    • Block：一组可协作的线程，可共享部分片上资源；一个 block 会整体安排到某个 SM。
    • Grid：一次 kernel 调用所包含的 blocks。
    • Warp：硬件实际协同调度的一组线程。线程走不同分支时，执行可能被串行化，降低效率。
    • SM：承担线程块执行和资源分配的 GPU 多处理器单元。寄存器、共享内存等有限资源会限制同时驻留的工作。

    Occupancy（占用率）常指一个 SM 上活跃 warp 数相对硬件上限的比例。它帮助判断并行度，但不是最终性能目标。高占用率不必然更快；低占用率有时也能因更高的每线程资源或更少的开销而表现不错。以 NVIDIA 最佳实践指南为准并实际测量。CUDA Best Practices Guide

    先用小到能画出来的数字算，弄懂规律再算大的。

    显存、张量与大模型内存估算

    第 4 周 · 把“显存不够”拆成可计算的问题
    学完后你可以：说出推理过程中主要显存消费者，并做一阶估算，而不是把模型参数量直接当作显存需求。

    一句话：显存要装三样东西：模型权重、每个请求的 KV cache、运行时的杂项；能接待多少并发，取决于权重放下之后还剩多少地方。

    用后厨来想：备菜台上摆着整本菜谱（权重，固定占地），每桌客人一张越写越长的记录卡（KV cache），再加上案板刀具（运行时开销）。菜谱越厚，留给记录卡的地方越少，能同时接待的桌数就越少。

    读完要能回答：

    • 7B 模型用 BF16 存，权重大约多大？
    • KV cache 的大小和哪些因素成正比？
    • 为什么“模型能放进显存”不等于“服务能跑起来”？

    4.1 推理显存由什么组成

    • 模型权重：参数需要存储。权重采用 FP16/BF16 时，每个参数通常约占 2 字节；FP8/INT8/INT4 等格式会改变存储量，但实际还受量化元数据和实现影响。
    • KV cache：自回归生成时保存已有 token 的 key/value 状态。上下文越长、并发序列越多、模型层和隐藏维度越大，缓存需求越高。
    • 临时工作区与激活：算子执行可能需要临时 buffer；训练时还会保留反向传播所需激活，训练显存通常明显高于单纯推理。
    • 框架与碎片余量：CUDA context、内存池、算子工作区和分配碎片都要留余量。
    一阶估算示例：一个 7B 参数模型仅按 BF16 权重粗略估算是 7×10⁹×2 bytes，约 14 GB（十进制）。实际部署还需要 KV cache、框架开销和运行余量，所以不能据此认定 16 GB 显存一定足够。单位换算、权重格式和实现细节也会带来差异。

    4.2 KV cache 为什么和服务容量相关

    模型生成每个新 token 时需要利用此前上下文。KV cache 减少重复计算，但要占用显存。对在线服务，容量规划不只是“模型能否加载”，还要看最大上下文、并发序列、输出长度和批处理策略。长上下文请求可能单独占用很多缓存空间，并挤压其他请求。

    因此服务容量会受多种因素共同限制：每请求状态的内存、每 token 的生成速度、调度策略和显存碎片。调整最大上下文和并发上限，可能比一味增加副本更有效。

    先看示范完整算一遍：Qwen2.5-7B 在 24 GB 显卡上能接几路 8K 上下文

    需要的四个数都在模型的 config.json 里。下面的数取自 Qwen2.5-7B，计算前请以你下载的文件为准。

    num_hidden_layers = 28 # 层数 num_key_value_heads = 4 # KV 头数（用了 GQA，比注意力头数 28 少很多） hidden_size / num_attention_heads = 3584 / 28 = 128 # head_dim 参数量约 76 亿
    1. 权重：76 亿 × 2 字节（BF16）≈ 15.2 GB。
    2. 每个 token 的 KV cache：2 × 28 层 × 4 个 KV 头 × 128 × 2 字节 = 57,344 字节，约 56 KB。
    3. 一路 8K 上下文：56 KB × 8,192 ≈ 448 MB。
    4. 能给 KV cache 的地方：24 GB 的卡，引擎按 0.9 的比例使用，约 21.6 GB；减去权重 15.2 GB，再减去约 1.5 GB 的运行时开销（估计值），剩约 4.9 GB。
    5. 能接几路：4.9 GB ÷ 448 MB ≈ 11 路满长度的 8K 请求。实际请求多数没用满 8K，能接的会更多。

    换到 16 GB 的 T4：权重 15.2 GB 已经超过可用显存，BF16 跑不起来，要用 4-bit 量化版（权重约 5 GB，估计值）。

    轮到你：按这几步做
    1. 选一个模型，从它的 config.json 抄出层数、KV 头数、hidden_size 和注意力头数。检查点：算出 head_dim，通常是 64 或 128。
    2. 分别用 BF16 和 INT8 算权重大小。检查点：INT8 正好是 BF16 的一半。
    3. 算每个 token 的 KV cache 大小，再乘以你想要的上下文长度。检查点：结果是 MB 到 GB 级；如果是 TB，检查是否多乘了一次。
    4. 用“可用显存 − 权重 − 运行时开销”算剩余空间，除以每路请求的 KV cache。检查点：得到一个并发数，并写明每个数字是查到的还是假设的。
    练习：建立显存估算表

    选一个你熟悉参数规模的模型，分别假设 FP16/BF16 与 INT8 权重，计算权重一阶容量。然后列出不能从权重公式直接得到的额外项目：KV cache、临时 buffer、运行时开销和安全余量。

    自测：权重只占 14 GB，为什么 16 GB GPU 仍可能 OOM？
    参考思路：模型运行还需要 KV cache、临时 buffer、CUDA/框架开销和分配余量。上下文、并发和批处理都可能进一步增加占用。
    自测：并发翻倍，KV cache 一定精确翻倍吗？
    参考思路：如果请求长度和模型配置相同、每个请求独立占缓存，趋势上接近随并发增长；但连续批处理、共享前缀、缓存策略、内存池和长度分布都会改变实际关系，必须测量。
    KV cache 一阶公式：KV cache 字节数 ≈ 2 × 层数 × KV 头数 × head_dim × 每元素字节数 × token 数 × 并发序列数。其中的 2 代表 K 和 V 两份。
    示例（假设结构：32 层、8 个 KV 头、head_dim=128、BF16）：每 token 约 2×32×8×128×2 = 131,072 字节（128 KiB）；一个 8K 上下文的序列约 1 GiB；32 个并发序列约 32 GiB，已经超过 7B 模型权重本身。若同模型用 32 个 KV 头（不做 GQA），缓存会是 4 倍。因此 GQA/MQA 这类减少 KV 头数的设计，对服务容量影响很大。具体数值请以目标模型的 config 为准。
    训练显存量级：常见的 Adam + BF16 混合精度训练，每个参数约需：BF16 权重 2 B + 梯度 2 B + FP32 主权重 4 B + Adam 两个状态 8 B ≈ 16 B/参数，7B 模型仅这一项就约 112 GB，还不含激活。这就是为什么训练需要多卡、分片（如 ZeRO/FSDP）、激活重计算，而同尺寸模型的推理可以单卡跑。实际数字随框架和优化器配置变化。
    练习参考答案：显存估算表
    以 7B 为例：BF16 权重约 14 GB，INT8 约 7 GB（量化元数据另计）。不能由权重公式得到的部分：KV cache（用上面的公式按最大上下文×并发计算）、临时 buffer、CUDA context 与框架开销、碎片余量。常见做法是给权重之外再预留 10%–20% 余量，并用压测校准。

    5.1 四类常见瓶颈

    瓶颈可能信号验证方向
    计算受限GPU 计算活动高，吞吐随计算资源或精度变化。对比不同输入规模/精度；检查算子计算量与设备利用。

    排队/服务受限请求延迟高但 GPU 计算并不繁忙，队列或 CPU 处理突出。拆分队列、预处理、模型执行、后处理和网络时延。

    5.2 推理服务常见指标

    • TTFT：Time To First Token，用户请求到收到首 token 的时间；队列、prefill 和网络都会影响。
    • Inter-token latency / TPOT：生成过程中相邻 token 的时间，关系到流式输出体感。
    • 吞吐：常见有 requests/s、input tokens/s 和 output tokens/s。要说明口径、模型和测试负载。
    • P50/P95/P99 延迟：均值掩盖尾延迟；生产服务要看分位数和错误率。
    • GPU 利用率与显存：要按 GPU、进程、Pod 和模型服务关联，并与请求量和延迟一起看。

    6.2 GPU 计时的两个常见坑

    • 异步执行：CPU 提交 GPU 工作后可能立即返回。若不在计时边界同步，测到的可能只是提交耗时。
    • 首次运行开销：首次调用可能包括初始化、内存分配、kernel 加载或编译等成本。需要预热，并将冷启动与稳态性能分开记录。
    • 重复运行与统计：多次运行，报告中位数和分位数；说明样本数和同步方式。
    • 内存池：框架可能保留已申请内存供后续复用，因此“已分配”和“设备上已保留”可能不是一个数字。
    先看示范一段可以直接运行的计时脚本，以及怎么读它的输出

    下面的脚本做了三件事：预热、同步后计时、多次测量取中位数。最后一列把耗时换算成算力，和规格表对比。

    import torch, time, statistics assert torch.cuda.is_available() for n in [512, 1024, 2048, 4096]: a = torch.randn(n, n, device="cuda", dtype=torch.float16) b = torch.randn(n, n, device="cuda", dtype=torch.float16) for _ in range(3): # 预热：第一次调用有初始化开销，不计入 a @ b torch.cuda.synchronize() times = [] for _ in range(20): t0 = time.perf_counter() c = a @ b torch.cuda.synchronize() # 等 GPU 真正算完再停表 times.append(time.perf_counter() - t0) med = statistics.median(times) tflops = 2 * n**3 / med / 1e12 # n×n 矩阵乘法约 2n³ 次运算 print(f"n={n:5d} 中位数 {med*1000:8.3f} ms 约 {tflops:6.1f} TFLOPS")

    怎么读：n 小的时候，算出来的 TFLOPS 远低于规格表，因为固定开销占了大头；n 越大越接近规格值。如果你在 T4 上看到最大一档只有规格值（约 65）的一半左右，属于正常现象，规格值是理想条件下的峰值。

    把 torch.cuda.synchronize() 那一行删掉再跑一次，耗时会小得离谱。这就是“没同步就计时”测到的只是“递工单”的时间。

    轮到你：按这几步做
    1. 在你的 GPU 上运行脚本，记录四行输出。检查点：n 越大，TFLOPS 越高。
    2. 删掉循环里的同步那一行再跑，对比结果。检查点：耗时明显变小，能解释原因。
    3. 把 device 改成 "cpu"、dtype 改成 torch.float32，对比 n=512 时 CPU 和 GPU 的耗时。检查点：能解释小任务时 GPU 为什么不一定更快。
    实验 A：矩阵大小

    比较 512、1024、2048 矩阵乘法的耗时；做预热，多次重复，记录中位数。注意矩阵增大后计算量增长很快，也要留意显存是否足够。

    实验 B：CPU 与 GPU

    比较同一运算在 CPU 和 GPU 的时间。确保包括合理的数据准备与同步；解释小任务为什么可能看不出 GPU 优势。

    实验 C：内存观察

    创建不同尺寸张量，观察 PyTorch 分配量变化；记录删除张量和缓存清理行为。不要将缓存清理作为生产服务的默认“优化”。

    自测：为什么只测一次矩阵乘法，结果不可信？
    参考思路：首次初始化、异步提交、系统噪声、时钟变化和偶然调度都会影响结果。要预热、同步、多次测量并记录条件。
    自测：PyTorch 显示的显存占用和 nvidia-smi 数字为什么可能不同？
    参考思路：PyTorch 有缓存分配器，可能保留已申请内存；进程上下文、库、其他进程和指标采样口径也会造成差异。需要区分框架 allocated/reserved 与设备级进程/全局视图。
    实验参考现象
    实验 A：矩阵边长翻倍，计算量约变为 8 倍，但小矩阵的耗时被启动开销主导，所以 512 到 1024 的耗时增长通常远小于 8 倍，越大越接近理论值。实验 B：小矩阵时 CPU 可能更快，因为拷贝和启动 kernel 的固定开销超过了计算本身。实验 C：删除张量后 memory_allocated 下降，但 memory_reserved 和 nvidia-smi 的数字不变，因为内存池留着备用。具体数字因硬件而异，记录你自己的结果并解释趋势。

    参考答案：不一定。被动监控没发现异常，不等于通过主动计算、显存、互连验证。节点准入策略应结合被动健康、软件状态、近期诊断和工作负载级验证。

    常见 XID大致含义典型处置
    13、31图形引擎异常 / GPU 显存页错误，多由应用或 kernel 非法访问引起先查应用、驱动与 CUDA 版本，不要急着换卡

    GPU 节点基线：上线前逐项确认

    • 持久模式：nvidia-smi -pm 1 或启用 nvidia-persistenced 服务，避免每次调用都重新初始化驱动。
    • 驱动与内核锁定：固定驱动版本，关闭内核自动升级；内核升了而驱动模块没有重编译，是重启后“卡不见了”最常见的原因。
    • NUMA 亲和：用 nvidia-smi topo -m 和 numactl --hardware 确认每张卡挂在哪个 NUMA 节点。数据加载进程与 GPU 不在同一节点时，拷贝会变慢。
    • 驱动升级流程：先在一台节点验证版本组合，再按“停止调度、排空、升级、重启、跑诊断、恢复调度”滚动进行，保留回滚用的旧版本安装包。
    • 准入检查：卡数与型号符合预期、无 XID 和 ECC 错误、PCIe 链路没有降速、dcgmi diag -r 1 通过、跑一次小负载验证。

    容器看不到 GPU：按第 2 章决策树逐层查；缓解是把 Pod 调到正常节点；恢复条件是测试 Pod 能跑通 nvidia-smi 和一个小算子。模型启动 OOM：查权重大小、最大上下文、显存预留比例、同卡是否有其他进程；缓解是减小上下文或并发、换量化版本或更大的卡。延迟高但利用率低：查排队请求数、CPU 是否打满、分词与前后处理耗时、网络与网关；缓解是扩 CPU 或拆分前处理。三类都要保留当时的指标截图、日志和 nvidia-smi -q 输出。

    第 8 周 · 把 GPU 认知接入 Kubernetes、资源管理与服务平台

    一句话：Kubernetes 管 GPU，就是把每台机器上的卡登记成资源，再按规则把任务派到有空卡的机器上。

    用后厨来想：每家门店向总部上报“本店有几个灶台”（device plugin）；总部调度中心按订单需要派单（调度器）；各部门有预订上限（配额）；VIP 来了，散客要让位（优先级与抢占）。

    读完要能回答：

    • Pod 怎么申请一张卡？

    8.1 Kubernetes GPU 资源路径

    1. GPU 节点安装并验证驱动、容器运行时和硬件。
    2. GPU device plugin 在节点上发现设备，并向 kubelet 注册扩展资源（常见资源名如 `nvidia.com/gpu`）。
    3. 工作负载声明 GPU 资源需求及节点选择条件。
    4. 调度器依据可用资源与其他约束安排 Pod；容器运行时把设备提供给容器。
    5. GPU 指标、Pod 状态和模型服务指标进入监控；健康异常触发摘除、隔离或人工检查。

    这条路径解决的是设备暴露与基本调度。它本身不替你解决公平排队、GPU 碎片、模型冷启动、资源配额、多租户隔离和服务 SLO。Kubernetes 官方 GPU 指南可作为基础参考。Schedule GPUs

    8.2 AI Infra 平台设计问题

    • 资源模型：用户申请的是整卡、分片、MIG 实例，还是一个模型服务副本？资源粒度如何表达？
    • 调度与优先级：在线推理和离线任务如何隔离？排队时间、优先级和配额怎么定义？Kueue 等队列系统可以帮助管理作业准入与配额。Kueue admission
    • 容量效率：GPU 利用率、服务尾延迟、显存碎片和扩容速度之间如何取舍？
    • 可靠性：节点健康异常时如何停止新任务、迁移或重启服务，如何避免反复调度到坏节点？
    • 成本与用户体验：模型冷启动、权重下载、预热和扩容时间会如何影响可用性与成本？

    8.3 异构卡型：让节点自动带上卡型标签

    国内集群很少只有一种卡。默认情况下，Kubernetes 只知道某台机器有几个 nvidia.com/gpu，不知道是 A100 还是 4090。手工给节点打标签，机器一多就会乱。

    GPU Feature Discovery（GFD）会自动探测每个节点的卡型、显存、驱动和 CUDA 版本，并写成节点标签。装了 GPU Operator 就自带它。

    kubectl get node <节点名> -o json | jq '.metadata.labels | with_entries(select(.key | startswith("nvidia.com/")))' # 常见标签（具体名称和取值以你集群里的实际输出为准）： # nvidia.com/gpu.product 卡型，如 NVIDIA-A100-SXM4-80GB # nvidia.com/gpu.memory 单卡显存（MiB） # nvidia.com/gpu.count 卡数 # nvidia.com/gpu.compute.major 计算能力的大版本 # nvidia.com/cuda.driver.major 驱动的大版本 # nvidia.com/mig.capable 是否支持 MIG

    有了标签，任务就能声明“哪些卡型可以接受、最想要哪一种”。下面的写法解决了“指定 A100 后，A100 全忙就一直 Pending，不会退而求其次”的问题：必须条件里列出所有可接受的卡型，偏好条件里给最想要的卡型更高权重。

    affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: nvidia.com/gpu.product operator: In values: ["NVIDIA-H100-80GB-HBM3", "NVIDIA-A100-SXM4-80GB"] # 这两种都能接受 preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 preference: matchExpressions: - key: nvidia.com/gpu.product operator: In values: ["NVIDIA-H100-80GB-HBM3"] # 优先 H100

    反过来也要防止“好卡被小任务占用”：给高端卡节点加污点（taint），只有声明了容忍（toleration）的大任务才能上去。

    8.4 碎片：两种碎片与装箱策略

    “集群明明还有空卡，任务却一直 Pending”，大多是碎片造成的。碎片分两种，原因和解法不同：

    卡数碎片显存碎片
    什么时候出现默认的整卡分配模式开启了按显存切分（如 HAMi）之后
    典型场景4 台 8 卡机器，每台都剩 2 张空卡，一共 8 张空闲；但一个要单机 8 卡的训练任务放不下4 张 80 GB 的卡，每张被小任务占了 60 GB，各剩 20 GB；一个要 40 GB 的任务放不下
    根本原因空卡被打散在不同节点上空显存被打散在不同的卡上
    主要解法节点级装箱：小任务尽量挤在同一批节点上，把整机留给大任务卡级装箱：小任务尽量挤在同一张卡上，把整卡留出来

    装箱（bin-packing）和打散（spread）是相反的两种策略。默认调度器的打分倾向于把任务分散到较空的节点上，这对高可用有利，却会制造卡数碎片。对 GPU 节点池，可以让调度器改成“优先选已经用得多的节点”：

    apiVersion: kubescheduler.config.k8s.io/v1 kind: KubeSchedulerConfiguration profiles: - schedulerName: gpu-binpack # 单独的调度器配置，只给 GPU 任务用 pluginConfig: - name: NodeResourcesFit args: scoringStrategy: type: MostAllocated # 越满的节点得分越高 resources: - {name: nvidia.com/gpu, weight: 10} - {name: cpu, weight: 1} - {name: memory, weight: 1}
    • GPU 任务在 Pod 里写 schedulerName: gpu-binpack 使用这套配置；在线服务仍可用默认的打散策略，保证副本分布在不同节点上。
    • Volcano 有 binpack 插件；HAMi 可以分别设置节点级和卡级的装箱或打散策略。
    • 按任务规模分节点池（例如整机训练池、单卡推理池、共享开发池），是减少碎片最直接的办法。
    • 值得监控的碎片指标：集群总空闲卡数，和“能放下的最大任务需要几张卡”。前者很大而后者很小，说明碎片严重。

    8.5 vGPU 与国内的切分方案

    除了 MIG、时间切片和 MPS，还有两类方案常被问到：

    • NVIDIA vGPU：在虚拟化平台上把一张卡分给多台虚拟机，切分比 MIG 灵活，但需要单独购买 NVIDIA 的软件授权，费用不低，多用于虚拟桌面和虚拟机场景。
    • 国内的切分方案：开源的 HAMi（支持 NVIDIA 和多种国产卡，见第 12 章），以及云厂商和创业公司的自研 GPU 虚拟化产品。
    • 评估时问四个问题：显存和算力是否真的隔离，一个任务出错会不会影响别人；对框架和推理引擎是否透明，要不要改代码；性能损耗有多大，要用自己的负载实测；是否支持你要用的国产卡，以及厂商能否长期维护。

    8.6 识别浪费：显存占满但算力闲着

    只看“分配出去几张卡”远远不够，要看卡分出去以后有没有真的在干活。一个典型的浪费信号是：显存占用很高，但算力利用率长期很低。下面的查询找出过去一小时这样的卡：

    ( DCGM_FI_DEV_FB_USED / (DCGM_FI_DEV_FB_USED + DCGM_FI_DEV_FB_FREE) > 0.8 ) and on (UUID) ( avg_over_time(DCGM_FI_DEV_GPU_UTIL[1h]) < 10 ) # 结果带有 namespace、pod 等标签（以你的 DCGM Exporter 输出为准），可以直接找到负责人
    注意一个例外：vLLM 这类推理引擎启动时会预先占满大部分显存给 KV cache（第 9 章），所以“显存高、算力低”在推理服务上只说明当前请求少，不一定是配置错误。对推理服务，要结合请求量判断：长期没什么请求，就该缩容、换小卡或改用共享。对训练和开发任务，这个信号通常就是真浪费，比如有人起了 Notebook 占着卡却没在用。
    另外，GPU_UTIL 只表示“有没有在算”。想看算力真实用了多少，可以启用 DCGM 的性能分析指标（如 DCGM_FI_PROF_SM_ACTIVE），它更接近真实负载，但需要在 exporter 里额外开启。

    8.7 落地清单：先做任务画像，再选方案

    不要先挑技术再找场景。先把集群里的任务分类，每一类对应一种方案：

    任务类型特点推荐做法
    大模型训练时间长、占整卡或整机、多卡要同时启动整卡分配；成组调度；独立的整机节点池；装箱策略
    在线推理（大模型）长期运行、要低延迟、显存需求大整卡或 MIG；专用节点池；高优先级；按排队数扩缩容
    小模型推理、向量与重排模型单个任务用不满一张卡时间切片或 HAMi 显存切分；共享节点池
    开发与 Notebook间歇使用、经常闲置共享卡；设置使用时长上限；闲置自动回收
    批量评测与离线任务不急、可以中断低优先级、可被抢占；借用其他队列的空闲额度
    1. 做任务画像：列出每类任务的数量、显存需求、对卡型和 CUDA 版本的要求、能否共享卡、能否被中断。
    2. 选切分方案：按上表给每类任务选整卡、MIG 或共享；混合场景用节点池隔开。

    4. 上排队系统：用 Kueue 或 Volcano 定义队列、配额、优先级和借用规则（8.2、第 11 章）。

    GPU 集群的运维一半是技术，一半是治理：谁先用、用多少、闲置了怎么收回，需要和业务团队一起定规则，写进制度，而不只是写进 YAML。

    自测：集群里有 8 张空卡，一个要 8 卡的训练任务却一直 Pending，可能是什么原因？怎么解决？
    最常见的是卡数碎片：8 张空卡分散在几台机器上，没有一台能单独提供 8 张。解决办法是对训练节点池使用装箱策略、按任务规模划分节点池；短期可以先让小任务迁走腾出整机。还要排除其他原因：卡型或标签不匹配、污点没有容忍、队列配额不足。
    自测：监控发现一个 vLLM 服务显存占用 90%、GPU 利用率只有 5%，是浪费吗？
    不一定。vLLM 启动时会预占大部分显存给 KV cache，显存高是正常现象。要看它的请求量：长期请求很少，就应该缩容、换小卡或改用共享；如果只是夜间低谷，属于正常的容量波动。

    资源怎么分1 张卡固定给在线模型，1 张给开发团队在线服务要稳定，不能和实验抢卡

    方式隔离适用与注意
    整卡独占强最简单；小模型会浪费
    MIG硬件级分片（显存与算力）仅部分数据中心 GPU 支持；分片规格固定，需要规划，调整可能要重置
    Time-slicing无显存隔离多个 Pod 分时共用；一个 Pod OOM 可能影响他人，适合开发/测试
    MPS弱多进程并发共享，可提高小负载利用率；故障域较大

    NVIDIA GPU Operator 把驱动、container toolkit、device plugin、DCGM Exporter、MIG manager 等组件用 Operator 统一部署和升级，是生产 K8s 集群常见的落地方式。DRA（Dynamic Resource Allocation）是 Kubernetes 较新的设备分配机制，用于表达比“数量”更丰富的设备需求；可用程度取决于集群版本，使用前请查官方文档。

    多租户与安全的基本做法

    • 按团队分命名空间并设配额：用 ResourceQuota 限制每个团队最多申请几张卡。
    • 优先级与抢占：在线推理用高优先级，离线任务用低优先级并允许被抢占。
    • 共享方式决定隔离强度：整卡和 MIG 隔离强；分时和软件切分隔离弱，不要让互不信任的租户共用一张卡。

    • 网络与凭证：模型服务默认只在集群内可达，对外统一走网关；API 密钥放在 Secret 里，不写进镜像和代码。

    9.1 推理的两个阶段

    Prefill 一次处理整段输入 prompt，计算密集，决定 TTFT；Decode 每次生成一个 token，要反复读取权重和 KV cache，通常受显存带宽限制，决定 TPOT。两者瓶颈不同，所以“GPU 很忙”不能直接等价于“服务很快”。

    9.2 推理引擎做了什么（以 vLLM 为例）

    • Continuous batching：不等整批请求全部结束，请求随到随插、随完随走，显著提高 GPU 利用率。
    • PagedAttention：把 KV cache 分成小块按需分配，减少碎片和浪费，让同样显存容纳更多并发序列。
    • 常见调参：--max-model-len（最大上下文）、--gpu-memory-utilization（引擎可使用的显存比例）、--max-num-seqs（并发序列上限）、--tensor-parallel-size（张量并行卡数）。参数名与默认值随版本变化，以所用版本文档为准。
    与第 4 章的连接：vLLM 启动时会按 gpu-memory-utilization 预留显存，权重之外的部分基本都划给 KV cache。所以“启动即占满显存”是正常现象，不等于泄漏；真正要看的是 KV cache 使用率、排队长度和被抢占/拒绝的请求。

    9.3 多卡并行与通信

    方式做法通信与适用
    数据并行/多副本每卡一份完整模型，各自服务请求几乎无卡间通信；模型放得下单卡时首选
    张量并行（TP）把每层的矩阵切到多卡每层都要 all-reduce，强依赖 NVLink；通常限制在单机内
    流水并行（PP）按层把模型切成几段分给不同卡/节点通信量较小，但有流水线气泡；可用于跨节点

    NCCL 是 NVIDIA 的多卡集合通信库（all-reduce 等），训练和 TP 推理都依赖它。互连决定上限：同机 NVLink > PCIe；跨机需要 InfiniBand 或 RoCE 等 RDMA 网络，GPUDirect RDMA 让网卡直接读写 GPU 显存，绕开 CPU 内存拷贝。

    nvidia-smi topo -m # 先看卡间是 NVLink 还是 PCIe NCCL_DEBUG=INFO python your_job.py # 日志里查看 NCCL 实际选用的通路 all_reduce_perf -b 8 -e 1G -f 2 -g 4 # nccl-tests：测 4 卡 all-reduce 带宽

    9.4 在 Kubernetes 上跑模型服务的坑

    • 共享内存：多进程推理常需较大的 /dev/shm，容器默认值太小会导致启动失败或卡死，需挂载 emptyDir（medium: Memory）。
    • 冷启动：权重动辄几十 GB，下载与加载时间长；用本地缓存/预热节点，readiness 探针要等模型加载完成再放流量。
    • TP 的调度约束：TP=4 就要求同一个 Pod 拿到 4 张互连良好的卡，调度和碎片问题比单卡严重。
    • 观测：采集引擎 /metrics（队列、KV cache 使用率、TTFT/TPOT）并与 DCGM 指标按 Pod 关联。

    自测：70B 模型 BF16 权重约 140 GB，为什么单张 80 GB GPU 放不下，需要 TP 或量化？
    权重本身已超过单卡显存，更不用说 KV cache 和运行余量。方案是 TP 切到多卡（例如 4 卡每卡约 35 GB 权重，再留给 KV cache），或量化到 INT8/INT4 后再评估是否放得下。选择时要同时考虑互连带宽、延迟和成本。
    自测：为什么 TP 通常限制在单机内？
    TP 每层都要做 all-reduce，通信非常频繁且延迟敏感。机内 NVLink 带宽高、延迟低；跨机走网络会明显拖慢每个 token 的生成。跨机更常用 PP 或多副本。
    自测：vLLM 服务启动后显存几乎占满，是内存泄漏吗？
    通常不是。引擎按 gpu-memory-utilization 预先分配 KV cache 池。应关注 KV cache 使用率、请求排队和抢占情况，以及显存是否随时间持续异常增长。

    读完要能回答：

    • 为什么扩缩容不看 GPU 利用率？
    • 为什么限流要按 token 而不是按请求数？
    • 给一个流量目标，怎么算出要几张卡、每百万 token 多少钱？

    10.1 扩缩容：别用 GPU 利用率

    LLM 服务的负载单位是 token 而不是请求，连续批处理下 GPU 利用率很早就接近“很忙”，对扩容几乎没有预警价值。更好的信号是排队请求数、KV cache 使用率、TTFT/TPOT 相对 SLO 的余量（引擎指标名随版本变化，以所用版本 /metrics 为准）。常用 KEDA 或 HPA + Prometheus 自定义指标实现。

    • 扩容慢是常态：调度 + 拉镜像 + 下载并加载几十 GB 权重可能是分钟级，所以要保留最小副本、提前预热，不能等排队了才扩。
    • 缩容要谨慎：缩掉的副本会丢掉在途请求和前缀缓存；设置较长稳定窗口并让引擎优雅排空。
    • 多信号保护：队列长度做主信号，P99 TTFT 做兜底告警。

    10.2 LLM 网关

    网关是多租户平台的控制点，通常承担：统一鉴权与路由（按模型/版本/租户）、按 token 计量的限流与配额、重试与降级、多后端容灾、请求与 token 日志、成本归因。把长上下文请求与短请求分池，可避免长请求挤占缓存、拖垮短请求的 TTFT。

    10.3 模型权重分发与灰度

    • 权重分发：镜像不要内置权重；用 PVC/本地 NVMe 缓存、节点预热或分层缓存，避免每个新 Pod 都全量下载。
    • 就绪判定：readiness 要等模型加载并完成一次预热推理后再放流量。
    • 灰度：新模型/新引擎版本按租户或比例小流量放量，对比 TTFT、TPOT、错误率和质量指标，保留一键回滚。

    10.4 压测与容量规划

    压测要用接近真实的输入/输出长度分布和并发，关注满足 SLO 前提下的吞吐（goodput），而不是峰值吞吐。可用引擎自带 benchmark 脚本或 NVIDIA GenAI-Perf 等工具，并固定模型、版本和长度分布。

    容量算法示例：峰值需处理 20,000 output tokens/s；压测得出单副本在“P95 TPOT ≤ 50 ms”约束下可持续 2,500 tokens/s。副本数 = 20,000 ÷ 2,500 = 8，再留 30% 余量（突发、故障、滚动发布）→ 10.4，取 11 个副本。再除以 GPU 小时单价得到“每百万 token 成本”，用它比较量化、GPU 型号和 TP/多副本方案。

    假设：用 T4 跑 4-bit 的 7B 模型；SLO 是 P95 TPOT 不超过 100 毫秒；压测得到单副本在 SLO 内能稳定输出 300 tokens/s（假设值）；高峰需要 1,500 tokens/s；T4 按量价格约 3.55 元/小时（2026 年 10 月的公开报价，以下单页为准）。

    1. 副本数：1,500 ÷ 300 = 5，加三成余量应对突发和故障，5 × 1.3 = 6.5，取 7 个。

    5. 实际利用率只有 40% 时：3.3 ÷ 0.4 ≈ 8.2 元。

    结论：成本主要由利用率决定。同样的卡，生意好时每百万 token 3 元，生意差时 8 元；这时候就要和 API 的报价比一比。

    11.1 平台需要知道的训练概念

    • 并行方式：数据并行（每卡一份模型，同步梯度）、FSDP/ZeRO（切片权重/梯度/优化器状态以省显存）、张量并行与流水并行（超大模型）。它们决定通信模式和对拓扑的要求。
    • MFU：模型实际 FLOPs 占硬件峰值的比例，是衡量训练效率的常用口径；偏低通常指向数据加载、通信或配置问题。
    • checkpoint：周期性保存训练状态，体量大（参数 + 优化器状态），写入吞吐和存储可靠性直接影响训练效率。

    11.2 平台侧四件大事

    • Gang 调度：多卡任务必须“全部资源就绪才启动”，否则部分 Pod 占着 GPU 等其余 Pod，多个任务互相等待。可用 Kueue、Volcano 等实现准入与成组调度。
    • 故障恢复：N 张卡同时跑，任务平均无故障时间约为单卡的 1/N。需要自动检测故障节点、替换并从最近 checkpoint 恢复。间隔取舍：越短写入开销越大，越长故障时损失越多（期望损失约为间隔的一半）。
    • 数据与存储：数据读取吞吐不足会让 GPU 空转；常用并行文件系统、NVMe 缓存或预取。
    • 拓扑感知：把同一任务放在互连近的节点上，减少跨交换机通信。

    11.3 训练卡死怎么查

    先判断是所有 rank 都卡还是个别 rank 掉队：看各 rank 日志与进度、NCCL_DEBUG=INFO 输出、dmesg 中的 XID、节点网络错误；用 py-spy dump 看进程栈卡在哪个集合通信；确认是否有 GPU 掉线、慢节点（straggler）或网络丢包。结论要落到“隔离哪个节点、重启哪个任务、从哪个 checkpoint 恢复”。

    假设一个训练任务平均每 24 小时故障一次，存一次 checkpoint 要 5 分钟（期间训练暂停）。

    存档间隔存档花掉的时间故障时平均丢掉的进度（间隔的一半）每天合计损失
    1 小时24 次 × 5 分钟 = 2 小时，约 8.3%0.5 小时，约 2.1%约 10.4%

    自测：为什么多卡训练任务需要 gang 调度？
    分布式训练要求所有 rank 同时在线。若只起了部分 Pod，它们会占着 GPU 等其余 Pod，其他任务同样如此，造成资源被占却无进展甚至互相死锁。Gang 调度保证要么整体就绪一起启动，要么都不启动。

    12.4 迁移时真正花时间的四件事

    • 算子覆盖与回退：不支持的算子会回退到 CPU 执行，功能看似正常但性能很差。要统计回退算子和它们的耗时占比。
    • 精度对齐：同一模型在不同卡上的输出要用固定输入和评测集对比，量化模型尤其要查。
    • 版本矩阵：固件、驱动、运行时、框架插件、推理引擎之间有严格的配套关系。把验证过的组合固化成基础镜像，不要在生产节点上各自升级。
    • 新模型跟进速度：开源新模型通常先支持 CUDA，国产栈的适配会滞后。评估时要问清厂商或社区的适配周期。

    12.5 多卡型混合集群怎么管

    • 按卡型分池：用节点标签和污点区分卡型，工作负载用 nodeSelector 或亲和性声明目标卡型，避免 Pod 被调度到跑不起来的节点。
    • 统一切分与调度：HAMi 这类异构算力虚拟化中间件可以把多家厂商的卡纳入同一套显存与算力切分模型；批任务与成组调度常配合 Volcano 或 Kueue。
    • 每种卡一套镜像：同一服务按卡型维护镜像变体，用同一份部署模板加变量切换，纳入 CI 构建。
    • 模型路由层屏蔽差异：网关按模型、租户和 SLO 把请求路由到不同卡型的后端池，上层业务只看到统一的 OpenAI 兼容接口。
    • 统一观测口径：各家 exporter 的指标名不同，在采集层归一成同一套标签（卡型、节点、设备、Pod），看板和告警才能复用。

    方式适合主要代价

    13.2 私有化部署开源大模型的标准路径

    1. 选模型与精度：国内常用 DeepSeek、通义千问（Qwen）等开源模型。按业务效果选最小够用的规模，再决定是否量化。
    2. 估显存与卡数：用第 4 章的方法算权重和 KV cache，按最大上下文与目标并发留余量。
    3. 选引擎：NVIDIA 卡常用 vLLM 或 SGLang；国产卡用对应的适配引擎（第 12 章）。
    4. 加网关：统一成 OpenAI 兼容接口，做鉴权、按 token 限流、审计日志和多模型路由（第 10 章）。
    5. 接监控：引擎指标、GPU 指标与网关指标三层关联，定义 TTFT 与 TPOT 的 SLO。
    6. 压测定容量：按真实的输入输出长度分布测 goodput，再定副本数。
    7. 写交付文档：部署步骤、版本矩阵、容量基线、故障 runbook 和升级回滚方案。
    小团队的起步方式：不必一开始就建集群。先用一台云 GPU 或现有的一两张卡，跑通“vLLM + 网关 + 监控”三件套，接入一个内部场景（知识库问答、代码助手、运维助手），拿到真实的并发和 token 用量，再决定扩容、换卡或迁到 Kubernetes。这条路径本身就是一份完整的作品集。

    • CPU 与架构：鲲鹏、飞腾是 ARM 架构，海光是 x86 架构。镜像要做多架构构建，依赖里的预编译包要确认有对应架构的版本。
    • 操作系统：常见的有 openEuler、麒麟和统信 UOS。内核版本与加速卡驱动的配套关系要提前核对。
    • 加速卡：按项目要求在昇腾、寒武纪、海光等范围内选型，用第 12 章的清单验收。
    • 中间件与数据库：项目可能要求国产数据库、消息队列和对象存储，平台组件要确认兼容。
    • 验收材料：常需要提供国产化清单、适配证明和测试报告，这些要在方案阶段就规划。

    13.6 成本口径：卡时、利用率与每百万 token

    国内谈算力成本常用“卡时单价”。把它换算成每百万 token 成本，才能和模型 API 的报价比较：

    换算示例（数值为假设）：单卡 10 元/小时，单卡副本在 SLO 内可持续 2,500 tokens/s。满载一小时可生成 2,500 × 3,600 = 900 万 token。
    平均利用率 30% 时，实际产出 270 万 token，成本约 3.7 元/百万 token；利用率提到 60% 时约 1.85 元/百万 token。
    结论：自建或租卡的成本主要由利用率决定。流量小或波峰波谷明显时，直接调用 API 往往更便宜；长期高负载或数据不能出域时，私有化才划算。
    先看示范从“300 人”算到“要几路并发”

    估算并发有一个通用公式：同时在处理的请求数 = 每秒到达的请求数 × 每个请求的处理时间。

    1. 在线人数：300 人，假设上班时间同时在用的有 20%，即 60 人。
    2. 请求频率：假设每人平均 3 分钟问一次，60 人每分钟一共 20 个请求，即每秒约 0.33 个。
    3. 每个请求的耗时：假设平均输出 400 字，按每秒 40 字算，约 10 秒。
    4. 平均并发：0.33 × 10 ≈ 3.3 路。
    5. 高峰：按平均值的 3 倍估，约 10 路并发。

    结论：这家公司高峰约 10 路并发。对照第 4 章的估算，一张 24 GB 的卡跑 7B 模型就能满足，再备一张做冗余。所有比例都是假设，上线后用真实的调用日志修正。

    轮到你：按这几步做
    1. 用这个公式，按你的假设估算 300 人的高峰并发。检查点：每个假设单独写一行，方便以后替换。
    2. 根据并发和上下文长度，用第 4 章的方法估算显存，选出卡型和卡数。检查点：卡数里包含冗余。
    3. 写权重和镜像从哪里来、怎么进内网。检查点：用到 ModelScope 或内部仓库，并有校验步骤。
    4. 写日志留存与访问控制、上线与回滚步骤。检查点：日志留存不少于六个月；回滚是一个能执行的动作。
    练习：写一份私有化部署方案

    假设一家 300 人的公司要给内部员工提供问答和代码助手，数据不能出公司网络。写 2 页方案：算力来源与卡型、模型与精度、并发与显存估算、引擎与网关、权重和镜像的获取方式、日志留存与访问控制、容量与每百万 token 成本、上线和回滚步骤。每个数字都写明假设。

    自测：公司想用开源大模型，什么情况下应该直接调 API，而不是自己部署？
    数据允许出域、流量小或波动大、团队没有 GPU 运维能力时，API 通常更省钱也更省事。数据不能出域、长期高负载、需要定制模型或有信创要求时，才值得私有化。
    自测：生产环境不能访问外网，模型服务怎么交付？
    提前在可联网环境准备固定版本的镜像包、模型权重、驱动与依赖安装包及校验值，导入内部镜像仓库和存储；部署脚本只引用内部地址；在干净机器上完整演练一次，并把版本矩阵和回滚步骤写进交付文档。
    自测：等保和日志留存要求，对大模型网关的设计有什么影响？
    网关要做身份鉴权和最小权限，记录谁在什么时间调用了哪个模型，日志集中留存不少于六个月并防篡改；提示词和输出可能含敏感信息，要按数据级别脱敏、控制访问并设定留存期限；管理操作要经过堡垒机并可审计。
    自测：卡时单价不变，为什么两家公司的每百万 token 成本可以差好几倍？
    差别主要来自利用率和 goodput：流量是否填满副本、是否做了连续批处理与量化、长短请求是否分池、是否按需缩容。利用率从 30% 提到 60%，单位成本就减半。
    练习参考要点：300 人公司的私有化方案
    一种合理的写法：假设同时在线 10%，高峰并发约 30；选 7B 到 14B 级的开源模型，BF16 或 AWQ 量化；按第 4 章估算，单张 24 GB 或 48 GB 卡可承载，再加一张做冗余；vLLM 加网关，按部门发密钥并按 token 限流；权重来自 ModelScope 并存入内部存储，镜像走内部仓库；网关日志留存六个月以上，提示词按数据级别脱敏；用实验 9 的方法压测得到 goodput 后换算每百万 token 成本；上线先灰度到一个部门，保留切回旧方案的开关。每个数字都注明是假设还是实测。

    14.6 怎么判断它有没有学会

    train.py 会打印每类的 precision、recall 和 f1-score。初学时先看 recall：某类真实告警里，模型找回了多少。混淆矩阵显示它把哪些类别互相弄混。不要只盯着一个总体准确率，尤其要关注真实业务中重要告警的漏判。

    1. 在 CSV 里给每个类别各补 10 条不同说法的练习告警。

    3. 挑 5 条没有放进 CSV 的新告警运行预测，手工记录哪些预测正确、哪些错误。

    一、基础题：GPU 与大模型（18 题）

    问题回答要点
    GPU 为什么适合深度学习？有大量并行执行单元，适合矩阵和张量这类能拆成许多相同小任务的运算；CPU 核少，擅长分支和流程控制。
    显存容量和显存带宽有什么区别？容量决定放得下多少权重和缓存；带宽决定每秒能读写多少数据，直接限制 decode 的出字速度。
    nvidia-smi 里的 GPU-Util 表示什么？采样周期内有计算在运行的时间占比。100% 不代表算力或带宽用满，低也不代表可以缩容。
    驱动、CUDA、框架之间是什么关系？驱动控制硬件，并决定最高支持的 CUDA 版本；CUDA 运行库通常随框架或镜像提供；框架通过它们调用 GPU。
    KV cache 是什么？显存怎么估？保存历史 token 在每层的 Key 和 Value，避免重复计算。约等于 2 × 层数 × KV 头数 × head_dim × 每元素字节数 × token 数 × 并发数。
    prefill 和 decode 有什么不同？prefill 并行处理全部输入，受算力限制，决定 TTFT；decode 逐个生成，每步读一遍权重，受显存带宽限制，决定 TPOT。
    TTFT、TPOT、吞吐分别受什么影响？TTFT 受排队、输入长度和 prefill 算力影响；TPOT 受显存带宽和批内并发影响；吞吐受批处理效率和 KV cache 容量影响。
    什么是连续批处理？请求不必等整批结束，可以随时加入正在运行的批次，完成的随时退出，从而提高 GPU 的利用效率。
    7B 模型用 BF16 要多少显存？16 GB 的卡够吗？权重约 14 GB。还要加 KV cache、运行时开销和余量，所以 16 GB 只能跑很短的上下文和很低的并发。
    量化是什么？代价是什么？把权重转成更低精度，省显存、提速度；代价是效果可能下降，必须用业务评测集验证。
    为什么训练比推理费显存得多？训练要额外保存梯度、优化器状态和反向传播用的中间结果。Adam 加混合精度大约每个参数 16 字节。
    张量并行和多副本怎么选？模型单卡放得下就用多副本，没有卡间通信；放不下才用张量并行，它每层都要通信，依赖 NVLink，一般不跨机。
    NVLink 和 PCIe 有什么区别？NCCL 是什么？NVLink 是 GPU 之间的专用高速互连，带宽远高于 PCIe；NCCL 是多卡集合通信库，会自动选择可用的最快通路。
    什么是 XID？举两个例子。驱动写入内核日志的 GPU 错误事件。79 表示 GPU 掉线，多为硬件、供电或链路问题；48 表示不可纠正的显存错误。
    显存 ECC 报错怎么处理？可纠正错误先观察趋势；不可纠正错误要隔离节点、保留日志，按厂商流程重置或报修。
    MIG、分时共享、MPS 有什么区别？MIG 是硬件级切分，隔离强但规格固定；分时共享没有显存隔离；MPS 让多个进程并发使用，效率高但故障会互相影响。
    给 GPU 代码计时为什么要先同步？GPU 调用是异步提交的，不同步的话测到的只是提交耗时，不是真正的执行时间。
    H20 的算力只有 H200 的约七分之一，为什么还能用来推理？它的显存容量和带宽并不低，而 decode 主要受带宽限制；吃亏的是训练和长输入的 prefill。

    二、基础题：Kubernetes 与平台（16 题）

    问题回答要点
    Kubernetes 怎么知道节点上有 GPU？厂商的 device plugin 向 kubelet 注册扩展资源并持续上报设备状态，节点的可分配资源里就会出现 nvidia.com/gpu。
    Pod 申请 GPU 时有什么限制？写在 limits 里，必须是整数，不能超卖；默认一张卡只能分给一个容器。
    容器是怎么拿到 GPU 的？NVIDIA Container Toolkit 在创建容器时把设备节点和驱动库注入进去，容器镜像里不需要装驱动。
    GPU Operator 包含哪些组件？驱动、容器工具链、device plugin、节点特征发现、DCGM Exporter、MIG 管理器等，用 Operator 统一部署和升级。
    device plugin 和 DRA 有什么区别？device plugin 只能表达“要几个”；DRA 可以按设备属性提出要求并支持共享，表达能力更强，可用程度取决于集群版本。
    默认调度器管 GPU 有哪些不足？没有成组调度和队列配额，不认识显存维度，拓扑感知弱，容易产生碎片。
    什么是成组调度？谁提供？任务的全部 Pod 都能拿到资源才一起启动，避免部分 Pod 占着卡空等。Volcano、Kueue 等提供。
    Kueue 和 Volcano 有什么区别？Kueue 负责作业排队、配额和准入，配合默认调度器使用；Volcano 是独立的批处理调度器，自带队列、成组和抢占。
    什么是 GPU 碎片？怎么缓解？每个节点都剩一两张卡，凑不出一个多卡任务。用装箱策略、按任务规模分节点池、必要时重调度来缓解。
    怎么保证在线推理不被离线任务挤占？在线服务用高优先级并放在专用节点池，离线任务低优先级、可被抢占，再用配额限制上限。
    模型服务的就绪探针要注意什么？要等模型加载并预热完才算就绪，失败阈值要留足加载时间，否则会被反复重启或过早接流量。
    为什么要调大 /dev/shm？推理和训练的多进程之间用共享内存传数据，容器默认只有 64 MB，不够时会启动失败或卡住。
    大模型服务用什么信号做扩缩容？排队请求数、KV cache 使用率和延迟相对 SLO 的余量。还要考虑新副本分钟级的冷启动。
    怎么把 GPU 指标对应到具体的 Pod？DCGM Exporter 在 Kubernetes 里会给指标加上 Pod、命名空间和容器标签，再和服务指标按这些标签关联。
    节点上一张卡坏了，平台应该自动做什么？标记设备不健康并停止调度，排空受影响的任务，告警并保留证据，修复后跑诊断再重新准入。
    多租户怎么做配额和成本分摊？按团队设保证额度和可借用上限，记录每个团队实际占用的卡时与 token 用量，按用量分摊。

    三、基础题：运维、网络存储与国内落地（14 题）

    问题回答要点
    驱动升级怎么做才安全？先在一台节点验证版本组合，再滚动进行：停止调度、排空、升级、重启、诊断、恢复，并保留旧版本用于回滚。
    服务器重启后 GPU 不见了，怎么查？看内核是否升级而驱动模块没有重编译，查内核日志和模块加载情况，再确认 PCIe 层面是否还能看到设备。
    Driver/library version mismatch 是什么原因？驱动的内核模块和用户态库版本不一致，常见于升级驱动后没有重启或重新加载模块。
    GPU 利用率呈锯齿状说明什么？GPU 在周期性地等数据。先查数据加载、存储吞吐和 CPU 预处理，而不是 GPU 本身。
    InfiniBand 和 RoCE 怎么选？InfiniBand 性能稳定但专用且贵；RoCE 跑在以太网上更通用，但要配好无损网络。看规模、预算和团队的网络能力。
    GPUDirect RDMA 是什么？让网卡直接读写 GPU 显存，不经过系统内存拷贝，用于多节点训练和高速存储。
    权重几十 GB，怎么缩短冷启动？权重放本地盘或节点缓存，提前预热节点，保留最小副本，就绪探针等加载完成后再放流量。
    国内环境拉不到镜像和模型怎么办？模型用 ModelScope 或镜像站，镜像走内部仓库的代理缓存，生产环境只从内部拉取，隔离环境提前做离线包。
    国产卡适配要验证什么？功能与回退算子、输出精度、SLO 下的吞吐与成本、长时间稳定性、监控与升级是否可运维。
    HAMi 解决什么问题？把多家厂商的加速卡纳入同一套显存与算力切分和调度模型，让多个 Pod 共享一张卡。
    信创环境对镜像构建有什么影响？鲲鹏、飞腾是 ARM 架构，镜像要做多架构构建，依赖里的预编译包要确认有对应版本，驱动要和国产操作系统的内核匹配。
    等保对模型服务有什么要求？身份鉴权与最小权限、操作可审计、日志集中留存不少于六个月、网络分区、漏洞与基线管理。
    自建和调用 API 怎么比成本？把卡时单价按实测吞吐和平均利用率换算成每百万 token 成本，再和 API 报价比；利用率低时 API 往往更便宜。
    消费级显卡能不能上生产？技术上能跑，但没有 ECC 和 NVLink，散热与供电不是按机房设计的，驱动许可对数据中心部署也有限制，要评估后再定。

    四、场景题（15 题）

    每题的回答骨架：先界定影响范围，再用指标缩小瓶颈，最后给出动作和验证方法。建议先自己口述一遍，再展开对照。

    场景：线上 P99 TTFT 突然升高，你怎么排查？
    ①范围：全部租户还是个别；是否伴随发布、流量或长上下文请求增加。②拆分：网关排队、引擎排队（waiting 请求数）、prefill 耗时、网络。③GPU/节点：KV cache 是否打满、有无抢占、XID/降频、节点是否异常。④动作：限流或分池长请求、扩容、回滚、摘除坏节点。⑤验证：TTFT 恢复，并补告警和 runbook。
    场景：集群 GPU 平均利用率只有 30%，怎么办？
    先确认口径（采样粒度、是否含空闲副本）和 SLO；再分类：预留过多、小模型独占整卡、批任务排队而在线卡空闲、并发低。对策：MIG/共享给小模型、在线与离线混部加优先级与抢占、量化或更大 batch、按需扩缩容。每项都说明风险（尾延迟、隔离性）。
    70B 模型要上线，你如何选部署方案？
    先算权重：BF16 约 140 GB，单张 80 GB 放不下。候选：TP 多卡（单机 NVLink 内）、量化后更少卡、PP/多机。再按目标上下文和并发算 KV cache 并留余量。然后压测对比 goodput、每百万 token 成本、故障域大小和调度难度，最后定副本数与发布策略。
    训练任务卡死，你怎么查？
    区分全体卡死与个别 rank 掉队；查各 rank 日志、NCCL 日志、dmesg XID、网络错误和节点状态；用 py-spy 看栈；锁定慢节点/故障节点后隔离，从 checkpoint 恢复，并把检测写入自动化。
    多团队共享 GPU 集群，如何做到公平又不浪费？
    资源模型（整卡/MIG/共享）、队列与配额（保证额度 + 可借用上限）、优先级与抢占规则、gang 调度、按团队归因的用量与成本、闲置回收。要说明在线推理与离线任务如何隔离，以及抢占的代价。
    怎样在不违反 SLO 的前提下降低推理成本？
    先测基线 goodput；再量化与更合适的 GPU 型号；提高 batch 与前缀缓存命中；长短请求分池；按 token 级信号扩缩容减少空闲；预留 + 按需组合。每一步都用“每百万 token 成本 + 质量指标 + SLO”验证。
    场景：公司要把一个跑在 A100 上的模型服务迁到昇腾 910C，你怎么推进？
    ①先定验收标准：功能、精度、SLO 下的 goodput、稳定性和成本。②搭最小环境，确认固件、驱动、CANN、框架插件和引擎的配套版本并固化成镜像。③跑通模型，统计回退算子，对比输出精度。④压测得到容量基线，和 A100 比较每百万 token 成本。⑤接入监控与告警，补故障码 runbook。⑥网关按权重灰度切流，保留回切能力。
    场景：老板要求一周内给公司内部上线一个私有化的大模型问答服务，你怎么做？
    先确认约束：数据级别、用户数与并发、可用算力。选一个够用的开源模型并估显存；用 vLLM 起服务，前面放网关做鉴权、限流和日志；接入基础监控；按真实问题长度压测定并发上限。先小范围试用，记录 token 用量和延迟，再给出扩容与成本方案。明确说明一周内不做的事，例如高可用和多模型路由。
    场景：客户机房完全隔离，要求信创环境，交付时最容易出什么问题？
    常见问题：镜像架构不匹配（ARM 与 x86）、内核与加速卡驱动不配套、缺离线依赖、权重文件校验失败、时间同步与证书问题。预防办法是提前拿到客户环境清单，在相同 CPU、操作系统和卡型的环境里完整演练，交付物带版本矩阵和校验值。
    场景：公司的卡一半是租的 H20，一半是自有的 4090，怎么分配负载？
    按特点分工：H20 显存大、带宽高，承担大模型和长上下文的在线推理；4090 显存小但单卡性价比高，承担小模型、向量与重排模型、开发测试和微调。两类卡分节点池，网关按模型路由。还要评估 4090 无 ECC、散热和驱动许可带来的生产风险。
    场景：模型服务每隔几小时就 OOM 重启一次，怎么查？
    ①看 OOM 的是显存还是主机内存，两者处理方式完全不同。②对照时间点：是否有超长上下文请求、并发突增或新模型加载。③显存：检查最大上下文与并发上限是否过于激进，是否有其他进程共用这张卡。④主机内存：看容器内存限制、共享内存、分词与前后处理是否堆积。⑤缓解：收紧上下文和并发上限，给长请求单独分池；验证：观察一个完整的业务周期。
    场景：推理引擎升级后吞吐下降了两成，怎么处理？
    先回滚保住线上，再定位。用同一份压测脚本和同一批参数对比新旧版本；检查默认参数是否变化、依赖和驱动是否同步变化、是否有算子回退到更慢的实现；把结论和基线数据写进发布记录，以后每次升级都跑同一套对比。
    场景：8 卡节点里有一张卡反复掉线，其他正常，怎么办？
    先把节点停止调度并排空，保留内核日志和 nvidia-smi -q 输出。按日志里的 XID 判断方向；检查这张卡的温度、功耗、PCIe 链路状态；有条件就和相邻槽位对调，判断问题跟着卡走还是跟着槽位走；确认是硬件问题后报修。恢复前跑诊断和一次小负载，再重新准入。
    场景：这个月算力成本超出预算四成，怎么分析？
    按团队、模型和环境拆开，看是用量增长还是利用率下降。常见原因：闲置副本没缩容、测试环境长期占卡、长上下文请求变多、小模型独占大卡。对应措施：按排队数缩容、给测试环境设时限、长短请求分池、小模型共享或换小卡。每项措施都估算能省多少，并说明对延迟的影响。
    场景：业务要求 P99 TTFT 小于 1 秒，高峰期达不到，有哪些办法？
    先拆分 TTFT 的构成：网关排队、引擎排队、prefill。排队占主要部分就扩容或限流；prefill 占主要部分就缩短提示词、启用前缀缓存、把长输入请求分池；还可以给高优先级业务预留副本。最后和业务确认 SLO 是否对所有请求都必要。
    作品集建议：整理成一个仓库：①GPU 节点准入与观测（DCGM、XID 告警）；②vLLM 压测报告（含 goodput 与容量成本表）；③K8s 部署（Operator、队列、HPA/KEDA）；④runbook 与一次故障演练复盘。简历按“问题 → 指标 → 动作 → 结果”写，并明确哪些已验证、哪些只是设计。

    五、系统设计（两个完整示例）

    回答顺序固定为六步：澄清需求、估算容量、画出架构、说明取舍、讲故障与观测、讲演进。下面的数字都是为了演示算法而做的假设。

    示例一：为一家 2,000 人的企业设计私有化的大模型推理平台

    1. 澄清需求：哪些场景（问答、代码助手、知识库）；数据能否出域；并发和延迟目标；是否有信创要求；现有算力和预算。
    2. 估算容量：假设高峰同时活跃 5%，即 100 人，平均每人每分钟一次请求、每次输出 300 token，峰值约 500 tokens/s；再给代码补全这类高频场景单独估一份。按实测的单副本容量加三成余量得出副本数。
    3. 架构：入口是大模型网关，负责鉴权、按 token 限流、审计和路由；后面按模型分成几个推理池，例如一个主力对话模型、一个代码模型、一组向量与重排模型；底层是 Kubernetes 加 GPU 调度；旁路有监控、日志和模型仓库。
    4. 关键取舍：一个大模型通吃，还是大小模型分工；整卡独占，还是小模型共享；全部自建，还是非敏感流量走 API；每一项都说明选择的理由和代价。
    5. 故障与观测：每个池至少两个副本并跨节点；节点故障自动摘除；指标分服务、引擎、GPU 三层；定义 TTFT 和可用性的 SLO 与告警。
    6. 演进：先单模型单池上线，拿到真实用量后再加模型、加扩缩容和多租户配额；国产卡作为独立的池逐步接入。

    示例二：设计一个 64 张卡的训练与推理混合平台，其中一半是国产卡

    1. 澄清需求：训练和推理各占多少；训练是微调还是大规模预训练；有几个团队；哪些模型已经适配了国产卡。
    2. 资源划分：按卡型分节点池；在线推理有固定的保证额度；训练和评测使用其余资源并可借用空闲的推理额度，但能被抢占。
    3. 调度：训练任务走批调度器，成组调度并带队列配额；推理服务用普通的 Deployment 加高优先级；小任务通过切分共享卡；多卡任务要求拓扑相近。
    4. 国产卡策略：先把已经适配好的推理模型放到国产卡池，训练和新模型留在 NVIDIA 池；每个模型维护“卡型、镜像、基线”对照表；网关按后端池路由。
    5. 存储与网络：数据集和 checkpoint 放共享存储，权重在节点本地缓存；多节点训练需要 RDMA 网络，单机多卡的微调不需要。
    6. 故障与运营：任务自动从 checkpoint 恢复；节点准入与隔离自动化；每周看利用率、排队时长、因故障损失的机时和各团队成本，再调整额度。

    自己再练两题：①为一个日调用一亿 token 的客服场景设计推理服务并估算成本。②客户机房完全隔离且要求信创，设计一套可离线交付的模型服务方案。

    术语表

    按需查阅，不需要一次记住。遇到正文里不认识的词，先来这里找。

    GPU
    图形处理器，也用于大规模并行数值计算。
    SM
    Streaming Multiprocessor，GPU 上承载线程块执行和资源分配的多处理器单元。
    Thread / Block / Grid
    CUDA 的逻辑执行层次：线程组成 block，blocks 组成一次 kernel 的 grid。
    Warp
    GPU 硬件协同调度的一组线程；分支分歧可能降低执行效率。
    Kernel
    由 CPU 发起、在 GPU 上执行的计算函数。
    HBM / VRAM
    GPU 本地显存技术/通称，保存权重、缓存和中间数据。
    显存带宽
    GPU 与本地显存之间单位时间的数据传输能力。
    PCIe / NVLink
    主机与设备、或 GPU 之间的数据互连技术。
    CUDA
    NVIDIA 的 GPU 计算平台与编程生态，包含编程模型、库、运行时和工具。
    Occupancy
    活跃 warp 相对于 SM 可支持最大 warp 数的比例；是分析线索，不是单独的性能目标。
    KV cache
    自回归模型生成时缓存已有 token 的 key/value 状态，以减少重复计算。
    OOM
    Out Of Memory，设备或主机可用内存不足导致分配或任务失败。
    TTFT
    Time To First Token，从请求进入到首个输出 token 可见的时间。
    TPOT
    Time Per Output Token，输出 token 生成阶段的平均时间指标之一。
    DCGM
    NVIDIA Data Center GPU Manager，用于数据中心 GPU 的管理、监控、健康和诊断。
    Device Plugin
    Kubernetes 扩展机制之一，供应商插件向 kubelet 注册 GPU 等设备资源。
    MIG
    Multi-Instance GPU，可将支持的 NVIDIA GPU 划分为隔离实例；是否可用依赖具体硬件与软件支持。
    NCCL
    NVIDIA Collective Communications Library，多 GPU/多节点通信库，常用于分布式训练与计算。
    Token
    文字被切成的片段，模型按 token 计算输入、输出和费用。
    Prefill / Decode
    推理的两个阶段：一次处理全部输入，然后逐个生成输出 token。
    精度（FP16、BF16、FP8、INT8）
    每个参数用多少位存储，决定权重大小和可用算力。
    量化
    把权重转换成更低精度以节省显存、提高速度，可能损失效果。
    FLOPS / TFLOPS
    每秒浮点运算次数，衡量算力；有稠密与稀疏两种口径。
    GQA
    分组查询注意力，让多个注意力头共用一组 Key 和 Value，从而缩小 KV cache。
    Continuous batching
    连续批处理，请求随到随加入正在运行的批次。
    TP / PP
    张量并行与流水并行，把一个模型拆到多张卡上的两种方式。
    All-reduce
    多卡之间汇总并同步数据的集合通信操作，训练和张量并行都依赖它。
    RDMA / RoCE / InfiniBand
    绕过内核的高速网络技术，用于多节点训练与存储。
    XID
    NVIDIA 驱动写入内核日志的 GPU 错误事件编号。
    ECC
    显存的错误检测与纠正；不可纠正错误通常意味着硬件问题。
    Checkpoint
    训练过程中保存的状态，用于故障后恢复。
    Gang 调度
    一个任务需要的全部资源同时就绪才启动。
    MFU
    模型实际运算量占硬件峰值算力的比例，衡量训练效率。
    LoRA
    只训练少量新增参数的微调方法，显存和时间开销小。
    FSDP / ZeRO
    把权重、梯度和优化器状态分片到多卡以节省显存的训练技术。
    NUMA
    多路服务器的内存与 CPU 分区；GPU 与进程不在同一分区时数据搬运会变慢。
    信创
    信息技术应用创新，指在关键行业采用国产 CPU、操作系统、数据库和加速卡等软硬件的要求。
    NPU / CANN
    华为昇腾的 AI 处理器及其计算架构，CANN 在昇腾栈里的位置相当于 CUDA。
    HAMi
    面向 Kubernetes 的异构算力虚拟化中间件，支持多家厂商加速卡的显存与算力切分和统一调度。
    Volcano
    Kubernetes 上的批处理调度系统，提供成组调度、队列和优先级等能力。
    智算中心
    以 AI 算力为主的数据中心，常以整机、整柜或卡时的方式对外提供算力。
    等保
    网络安全等级保护制度，按系统定级提出安全技术与管理要求。
    MaaS
    Model as a Service，以 API 方式按用量提供模型能力。
    Goodput
    满足延迟 SLO 前提下的有效吞吐，用于容量规划。
    卡时
    一张加速卡使用一小时，国内算力租赁常用的计价单位。
